Frühe Version. v0.2.0 ist durch Tests und Dry-Runs abgedeckt, wurde aber noch nicht gegen die echten Stores ausgeführt. Jeder Befehl, der in einen Store schreibt, unterstützt --dry-run; beginnen Sie mit reinen Lesebefehlen wie appship status.

Mit einem KI-Agenten einrichten

Fügen Sie einen dieser Prompts in Claude Code, Codex, Antigravity, Cursor oder einen anderen KI-Coding-Agenten ein, der im Stammverzeichnis Ihres Projekts geöffnet ist. Der Agent installiert und konfiguriert appship und hält an, sobald eine Entscheidung bei Ihnen liegt. appship selbst ruft nie eine KI auf: Die Prompts sind reiner Text, und der Agent läuft mit Ihrem eigenen Konto.

  • Der Agent schreibt nur in einen Store, wenn Sie es verlangen, und führt vorher --dry-run aus. --yes fügt er erst hinzu, nachdem Sie den Dry Run freigegeben haben, denn das Terminal eines Agenten kann die Bestätigungsabfragen von appship nicht beantworten.
  • Er öffnet, zeigt oder committet nie Schlüsseldateien. Die Schlüssel fügen Sie selbst mit appship credentials add hinzu.
  • Er committet und pusht nicht. Lesen Sie trotzdem jeden Befehl, bevor Sie ihn erlauben.

Die Prompts sind auf Englisch, damit jeder Agent sie gleich versteht. Der Agent antwortet in der Sprache, in der Sie schreiben.

Ein Projekt einrichten

Einmal pro Projekt, auch auf einem Rechner ohne fastlane oder appship. Deckt die Schritte 2 bis 6 dieser Anleitung ab; die Store-Schlüssel erstellen Sie weiterhin selbst.

prompt
Set up appship-ai in this project so I can release it to the App Store and Google Play.
appship is a CLI that wraps fastlane. Guide: https://appship.ketchsoft.com/docs.html

1. Check node (22+), fastlane and appship (`appship --version`). Tell me what is missing and ask before installing anything globally (`brew install fastlane`, `npm i -g appship-ai`).
2. Run `appship init --yes --agents <you>` at the project root, where <you> is claude, codex or antigravity (the agent you are; use claude if none fits). Compare release/release.yml with the project (build_command, artifact paths, bundle id, package name), fix what is wrong and tell me what you changed.
3. Store keys: tell me what I need (App Store Connect API key, Google Play service account JSON) and how to create them, following "Get store keys" in the guide. I will run `appship credentials add <profile>` in my own terminal. Then set credentials.profile in release.yml.
4. Fill the store content with the skills that init installed: app-content for release/questionnaire.yml, the listing text in release/*/metadata, then store-screenshots. If the skills are not loaded in this session, read their SKILL.md files in .claude/skills/ or .agents/skills/ and follow them. If the app is already live, ask me whether to run `appship metadata pull` first. Ask me for anything the code cannot tell you; leave contacts, demo accounts and passwords as TODO until I give them.
5. Run `appship doctor` and fix until there is no ✗. List the remaining warnings (!).
6. Finish with a short summary: what is done, what I still have to do by hand, and the next command to run.

Rules:
- Never run a command that writes to a store (upload, metadata push, submit, promote, first-release, signing import) unless I ask. Then run it with --dry-run first and wait for my OK. Add --yes only after I approved the dry run in this chat.
- Never open, print, copy or commit key files (*.p8, *.p12, *.jks, *.keystore, service account JSON) or anything in release/keys/.
- Do not commit or push.
- Reply in the language I write in.

CI einrichten (GitHub Actions)

Sobald das Projekt eine release/release.yml hat. Passt den Workflow aus „In der CI ausführen“ an und listet die Secrets auf, die Sie anlegen müssen.

prompt
Set up GitHub Actions to release this project with appship-ai. The project already has release/release.yml.
Guide: https://appship.ketchsoft.com/docs.html#ci

1. Start from https://raw.githubusercontent.com/ketchstudio/appship-ai/main/examples/github-actions.yml. Save it as .github/workflows/release.yml and adapt it to this project: platforms, toolchain setup, build steps, Android keystore, and the iOS signing method in use (fastlane match, files from the account owner with `appship signing import --keychain`, or automatic signing).
2. Keep `appship doctor` as the first appship step. Store-writing steps need --yes in CI; keep submit behind the manual `submit` input.
3. List every secret I must add in Settings → Secrets and variables → Actions, with the command that produces each value (for example `base64 -i AuthKey_XXXX.p8 | pbcopy`). I add the secrets myself. Never read or print key files and never write a key value into a file.
4. Creating the iOS app and uploading App Privacy need an Apple ID with 2FA and cannot run in CI. If this project still needs them, tell me to run them locally once.
5. Show me the final workflow and the list of secrets. Do not commit or push until I say so.

Reply in the language I write in.

Bei jedem Release

Erhöht die Version, schreibt die Release Notes in allen Sprachen, testet den Upload per Dry Run und wartet auf Ihr OK.

prompt
Prepare a new release of this project with appship-ai (already set up in release/).

1. Find the current version and build number (pubspec.yaml, build.gradle, the Xcode project or Info.plist, package.json: whatever this project uses) and read the git log since the last tag. Propose the next version and build number, and change them once I agree.
2. Write the release notes for every locale with the release-notes skill (read its SKILL.md in .claude/skills/ or .agents/skills/ if it is not loaded).
3. Run `appship doctor` and fix the errors.
4. Run `appship upload --build --dry-run`, show me what would be sent, and stop.

When I approve, run `appship upload --build`. When I later ask to submit, run `appship submit --dry-run` first and wait for my OK again. Add --yes only after I approved the dry run in this chat. Never open or print key files. Do not commit or push unless I ask.

Reply in the language I write in.

iOS-Signierung ohne Inhaberzugriff

Wenn Ihnen der Kontoinhaber eine .p12 und Provisioning-Profile gegeben hat. Hintergrund: iOS-Signierung ohne Inhaberzugriff.

prompt
Set up iOS code signing for this project with appship-ai. I am not the account owner; the owner gave me a .p12 (Apple Distribution certificate) and App Store .mobileprovision files.
Guide: https://appship.ketchsoft.com/docs.html#not-owner

1. Ask me where the files are. They must be inside release/keys/ (gitignored); tell me to move them there if they are not. Do not open, print or copy them yourself.
2. Add an ios.signing block to release/release.yml (style: manual, certificate, profiles: one per bundle id, including extensions).
3. Change ios.build_command so the build uses "$APPSHIP_EXPORT_OPTIONS" (for Flutter: --export-options-plist="$APPSHIP_EXPORT_OPTIONS"; for xcodebuild/gym: the matching export options flag).
4. Run `appship signing import --dry-run` and show me the result. I will run the real import in my own terminal, because it asks for the .p12 password.
5. Run `appship doctor` and explain every signing error or warning (profile type, expiry, team, bundle id, certificate in the keychain).

Never commit anything in release/keys/. Do not commit or push unless I ask. Reply in the language I write in.

2Installation

Installieren Sie appship einmal pro Rechner, global. Ihrer App-package.json wird nichts hinzugefügt.

terminal
npm i -g appship-ai
appship --version

Das Paket heißt appship-ai und installiert den Befehl appship. Um es ohne Installation auszuprobieren, führen Sie npx appship-ai --help aus.

3Store-Schlüssel besorgen

Das erledigen Sie einmal pro Entwicklerkonto, nicht pro Projekt. Mit beiden Schlüsseln können Builds in Ihrem Namen veröffentlicht werden, committen Sie sie daher niemals in git.

iOS: App-Store-Connect-API-Schlüssel

  1. Öffnen Sie in App Store Connect Users and Access → Integrations → App Store Connect API.
  2. Klicken Sie unter Team Keys auf +. Nennen Sie ihn appship und geben Sie ihm die Rolle App Manager.
  3. Laden Sie AuthKey_XXXXXXXXXX.p8 herunter. Apple erlaubt den Download nur ein einziges Mal.
  4. Notieren Sie die Key ID (10 Zeichen, auch im Dateinamen) und die Issuer ID (die UUID über der Schlüsseltabelle).

Team Keys können nur vom Account Holder oder von Admins erstellt werden. Falls Sie das nicht sind, bitten Sie den Inhaber, Ihnen den Schlüssel zu schicken, oder lesen Sie iOS-Signierung ohne Inhaberzugriff für einen individuellen Schlüssel.

Eine Apple-ID (E-Mail) ist optional. Sie wird nur benötigt, um den App-Eintrag anzulegen und die App-Privacy-Angaben hochzuladen, da der API-Schlüssel von Apple beides nicht kann. Sie erfordert 2FA und funktioniert deshalb nie in der CI.

Android: Google-Play-Dienstkonto

  1. Wählen Sie in der Google Cloud Console ein Projekt aus und aktivieren Sie die Google Play Android Developer API.
  2. Gehen Sie zu IAM & Admin → Service Accounts → Create service account. Es ist keine GCP-Rolle nötig.
  3. Öffnen Sie das Konto und laden Sie über Keys → Add key → JSON die Schlüsseldatei herunter.
  4. Gehen Sie in der Play Console zu Users and permissions → Invite new users und laden Sie die client_email aus der JSON-Datei ein. Erteilen Sie Release apps to testing tracks, Release to production und Manage store presence.
  5. Warten Sie einige Minuten, bis die Berechtigungen wirksam werden. Bei einem neuen Konto kann es bis zu 24 Stunden dauern.

Als Profil speichern

Ein Profil kopiert die Schlüssel mit Modus 600 nach ~/.appship/credentials/<name>/, sodass alle Projekte auf diesem Rechner sie gemeinsam nutzen können. Führen Sie den Befehl ohne Flags aus, um Schritt für Schritt gefragt zu werden.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4Projekt einrichten

Führen Sie init im Stammverzeichnis Ihres App-Repos aus.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init erkennt Flutter-, React-Native-, Cocos-Creator- oder native Projekte, liest Ihre Bundle-ID und den Paketnamen und trägt Build-Befehl und Artefaktpfad ein. Es legt diesen Ordner an und ergänzt release/keys/* und release/.appship/ in .gitignore:

project layout
my-app/
└── release/
    ├── release.yml            # IDs, Artefakte, Build-Befehle, Tracks, Zugangsdaten
    ├── questionnaire.yml      # Antworten auf Store-Fragen
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # in .gitignore; nur wenn Sie kein Profil nutzen
    └── .appship/              # in .gitignore; temporäre Dateien für fastlane

Öffnen Sie release/release.yml und prüfen Sie artifact und build_command für jede Plattform. Für eine Flutter-App sieht das so aus:

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # sofort veröffentlichen, sobald Apple freigibt
    phased_release: false      # 7-tägiger gestaffelter Rollout
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # draft, solange die App unveröffentlicht ist
  rollout: 1                   # 0.2 = 20 % gestaffelter Rollout
credentials:
  profile: my-company

Committen Sie den gesamten Ordner release/ außer keys/ und .appship/. Ihr Repo erhält kein Fastfile: Die Release-Logik bleibt in appship, sodass ein Update von appship jedes Projekt aktualisiert.

5Store-Eintrag ausfüllen

Wenn die App bereits live ist, laden Sie den aktuellen Eintrag herunter, statt ihn abzutippen:

terminal
appship metadata pull

Andernfalls ersetzen Sie jedes TODO in diesen Dateien:

  • release/questionnaire.yml: Altersfreigabe, Exportvorschriften, Inhaberrechte, Kontakt für den Reviewer, App Privacy und die Android-Angaben unter „App content“.
  • Text: release/ios/metadata/<locale>/*.txt und release/android/metadata/<locale>/*.txt.
  • Release Notes pro Sprache: ein Ordner pro Locale. Siehe unten Sprachen und Release Notes.
  • iOS-Screenshots in release/ios/screenshots/<locale>/: mindestens ein Satz für iPhone 6,9" (1320×2868) oder 6,5" (1284×2778).
  • Android-Bilder in release/android/metadata/<locale>/images/: icon.png 512×512, featureGraphic.png 1024×500 und mindestens 2 Bilder in phoneScreenshots/.

Sprachen und Release Notes

Beide Stores nehmen für jede Sprache einen eigenen „What's New“-Text entgegen. Jede Sprache ist ein Ordner, und jeder Ordner enthält seine eigenen Release Notes:

StoreDatei, eine pro Locale-OrdnerMax.
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 Zeichen
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 Zeichen

So fügen Sie eine Sprache hinzu:

  1. Tragen Sie sie in release.yml ein. Die Liste ist optional; ohne sie verwendet appship jeden Ordner, den es findet. iOS und Android nutzen unterschiedliche Locale-Codes, daher hat jede Plattform ihre eigene Liste:
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # Play-Codes weichen ab, z. B. hier zh-CN, unter iOS zh-Hans
  2. Legen Sie den Ordner an, zum Beispiel release/ios/metadata/vi/, und füllen Sie die erforderlichen Dateien aus: unter iOS name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt und release_notes.txt; unter Android title.txt, short_description.txt, full_description.txt und changelogs/default.txt.
  3. Fügen Sie iOS-Screenshots in release/ios/screenshots/<locale>/ hinzu. Für Android aktivieren Sie die Sprache zuerst in der Play Console.
  4. Führen Sie appship doctor aus. Eine aufgelistete Locale ohne Ordner ist ein Fehler. Ein Ordner, der nicht aufgelistet ist, ergibt eine Warnung, weil er trotzdem in den Store übertragen wird.

Gut zu wissen:

  • Sie müssen die Sprache nicht zuerst in App Store Connect hinzufügen. Sie wird beim Übertragen der Metadaten angelegt.
  • Lassen Sie release_notes.txt bei der allerersten Version einer App leer. Apple akzeptiert bei Version 1.0 keine Release Notes.
  • Eine Locale ohne Release Notes zeigt in dieser Sprache ein leeres „What's New“. doctor warnt, wenn manche Locales Notes haben und andere nicht.
  • iOS-Ordnernamen müssen einer der Apple-Codes sein, etwa en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans oder zh-Hant. doctor lehnt alles andere ab, zum Beispiel zh-CN.
  • Der gemeinsame Ordner default von fastlane wird noch nicht unterstützt.

Empfohlene Sprachen

Sie wissen nicht, welche Sprachen Sie als Nächstes hinzufügen sollen? appship schlägt sechs Sprachen mit großer Reichweite vor: Spanisch (Spanien und Lateinamerika), brasilianisches Portugiesisch, Deutsch, Französisch, Japanisch und Koreanisch. Die beiden Stores verwenden unterschiedliche Codes:

Portugiesisch, Brasilienpt-BRpt-BRpt-BR

  • Legen Sie die Ordner beim Einrichten eines Projekts an: appship init --locales preset für alle sechs oder --locales es,ja für einzelne. Der Befehl schreibt locales für jede Plattform mit den richtigen Codes und erstellt Eintragsdateien, die mit TODO gefüllt sind und von Ihnen übersetzt werden müssen. doctor schlägt fehl, bis jedes TODO ersetzt ist.
  • Bei einem bereits bestehenden Projekt legen Sie die Ordner mit den obigen Codes von Hand an (init --force würde release.yml überschreiben).
  • Behalten Sie nur die spanische Variante, die Sie wirklich schreiben werden. es-MX unter iOS und es-419 bei Play decken ganz Lateinamerika ab.
  • Die Store-Limits zählen Zeichen, nicht Bytes oder Wörter. Japanische und koreanische Texte sind meist kürzer als englische; deutsche und französische sind länger und stoßen oft ans Titellimit von 30 Zeichen.
  • Aktivieren Sie jede Sprache in der Play Console, bevor Sie hochladen. doctor warnt vor einem Android-Ordner, der kein Play-Sprachcode ist, und schlägt die Korrektur vor, zum Beispiel muss aus ja dann ja-JP werden.
  • Der Skill release-notes kennt die Konventionen jeder Sprache: förmliche oder informelle Anrede, regionale Varianten, japanische Satzzeichen in Vollbreite und den Leerraum im Französischen vor ? ! : ;.

Release Notes mit einem KI-Coding-Agenten schreiben

appship init installiert einen Skill namens release-notes für Ihren KI-Coding-Agenten (Claude Code, Codex oder Antigravity): in .claude/skills/ für Claude Code, in .agents/skills/ für Codex und Antigravity. Bitten Sie den Agenten vor einem Release, „die Release Notes für diese Version zu schreiben“ (oder führen Sie in Claude Code /release-notes aus, in Codex $release-notes). Der Skill wird:

  1. release.yml und die Locale-Ordner lesen.
  2. git log seit dem letzten Tag lesen, sowie CHANGELOG.md, falls vorhanden.
  3. Kurze, nutzerorientierte Notes in Ihrer Hauptsprache schreiben und in jede andere Locale übersetzen.
  4. Die Store-Limits einhalten, die Dateien schreiben und dann appship doctor ausführen.

Die Notes bleiben einfache Dateien, Sie können sie also prüfen und bearbeiten. Der Skill fragt nach, bevor er vorhandenen Text überschreibt, und überträgt nie etwas in einen Store.

Screenshots und Store-Angaben mit einem KI-Agenten

init installiert daneben zwei weitere Skills. Wie release-notes schreiben sie nur Dateien in release/, führen appship doctor aus und überlassen das Übertragen in die Stores Ihnen.

  • store-screenshots: plant die Aufnahmen mit Ihnen, nimmt sie im iOS-Simulator oder in einem Android-Emulator auf, ergänzt pro Sprache eine übersetzte Überschrift und rendert jedes Bild in einer Größe, die der jeweilige Store akzeptiert (iPhone 6.9" 1320×2868, iPad 13", wenn die App auf dem iPad läuft, Play 1080×1920), dazu das Play-Icon und die Feature-Grafik.
  • app-content: füllt release/questionnaire.yml (Altersfreigabe, App Privacy, Exportvorschriften, Datensicherheit, Einstufung des Inhalts, Zielgruppe, Werbung, App-Zugriff) anhand Ihrer Abhängigkeiten, Berechtigungen und Ihres Codes aus, fragt Sie nach dem, was der Code nicht zeigen kann, und hält die Antworten zwischen beiden Stores konsistent.
AgentSkill-OrdnerAufruf
Claude Code.claude/skills//store-screenshots
Codex.agents/skills/$store-screenshots oder /skills
Antigravity.agents/skills/bitten Sie „use the store-screenshots skill“

appship ruft selbst nie eine KI auf. Öffnen Sie den Agenten im Stammverzeichnis des Projekts, angemeldet mit Ihrem eigenen Konto, und bestätigen Sie die Befehle, die er ausführen möchte.

Wählen Sie die Agenten bei init aus, oder installieren und aktualisieren Sie die Skills später, etwa nach einem Upgrade von appship:

terminal
appship init --agents all             # Skills für Claude Code, Codex und Antigravity
appship skills                        # welche Skills jeder Agent hat
appship skills add --agent codex      # für Codex / Antigravity installieren (.agents/skills/)
appship skills add --force            # durch die Skills dieser Version ersetzen

6Mit doctor prüfen

doctor prüft Tools, Konfiguration, Schlüssel, Artefakte, Zeichenlimits, Bildgrößen und Platzhaltertexte und schlägt fehl, wenn eine Schlüsseldatei von git verfolgt wird. Wiederholen Sie den Lauf, bis kein ✗ mehr erscheint. Ein ! ist eine Warnung und blockiert kein Release.

appship doctor
▸ Security
  ✓ No key files tracked by git
  ✓ .gitignore protects release/keys/
▸ iOS · store listing
  ✗ ios/metadata/en-US/subtitle.txt is 34 characters (max 30)
▸ Android · store listing
  ✓ Metadata OK for en-US

  ✗ 1 error(s), 0 warning(s)

7Erstes Release

terminal
appship build
appship first-release --create-app
  • iOS: legt die App in App Store Connect an (benötigt die Apple-ID und fragt eventuell nach einem 2FA-Code) und überträgt dann Eintrag, Screenshots, Altersfreigabe, Review-Infos und App Privacy.
  • Android: Google Play bietet keine API zum Anlegen einer App, daher gibt appship stattdessen die Schritte aus.
  • Beide schreiben release/CHECKLIST.md: die Konsolenschritte, die von Hand erledigt werden müssen, mit Ihren Antworten aus questionnaire.yml zum Kopieren.

Folgen Sie bei Google Play der Checkliste, um:

  1. die App in der Play Console anzulegen.
  2. das Dienstkonto zur App einzuladen.
  3. die erste .aab von Hand in Internal testing hochzuladen.
  4. den Abschnitt „App content“ auszufüllen.

Solange die Android-App noch nie veröffentlicht wurde, setzen Sie release_status: draft in release.yml. Neue persönliche Entwicklerkonten benötigen vor der Produktion außerdem einen geschlossenen Test mit 12 Testern über 14 Tage.

Schließen Sie dann das erste Release ab:

terminal
appship metadata --android
appship upload
appship submit

8Jedes weitere Release

Erhöhen Sie Version und Build-Nummer in Ihrem Projekt, dann:

terminal
# den KI-Agenten die Release Notes schreiben lassen (siehe Sprachen und Release Notes)
appship upload --build   # bauen, dann TestFlight + Google-Play-Track (standardmäßig internal)
# auf TestFlight / im internal Track testen
appship submit           # iOS: App Review · Android: auf production hochstufen
appship status           # Review-Status und Versionen in beiden Stores

Für einen gestaffelten Rollout auf Android:

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

Jeder Befehl, der in einen Store schreibt, fragt zuerst nach Bestätigung. Fügen Sie --dry-run hinzu, um genau zu sehen, was gesendet würde.

9In der CI ausführen

In der CI stammen die Schlüssel aus Secrets über APPSHIP_*-Umgebungsvariablen, und jeder Schreibbefehl benötigt --yes. Legen Sie diese Repository-Secrets an (in GitHub: Settings → Secrets and variables → Actions):

SecretWert
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYAusgabe von base64 -i AuthKey_XXX.p8
APPSHIP_PLAY_JSONAusgabe von base64 -i play-service-account.json
Signatur-SecretsHängen davon ab, wie Sie signieren, zum Beispiel MATCH_PASSWORD für fastlane match oder ein Android-Keystore in base64

Die Release-Schritte eines GitHub-Actions-Workflows:

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # iOS-Builds benötigen macOS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...Ihre Toolchain, fastlane und Signierung einrichten...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Ergänzen Sie Ihr eigenes Flutter-Setup, den Signierschritt und, falls Sie submit manuell auslösen möchten, einen workflow_dispatch-Input wie den oben gezeigten.

  • Das Anlegen der iOS-App und der Upload von App Privacy benötigen die Apple-ID mit 2FA. Erledigen Sie das einmalig auf Ihrem Rechner, nicht in der CI.
  • Um eine fastlane-Version festzulegen, verwenden Sie ein Gemfile und setzen APPSHIP_FASTLANE="bundle exec fastlane".
  • Testen Sie die Pipeline mit --dry-run vollständig, bevor Sie sie etwas übertragen lassen.

Referenz

Signierung

appship baut und signiert Ihre App nicht. Es führt Ihren build_command aus und übernimmt das signierte Artefakt.

  • iOS: Am einfachsten ist die automatische Signierung in Xcode (Signing & Capabilities). Für Teams und die CI nutzen Sie fastlane match.
  • Android: Erstellen Sie einen Upload-Keystore, konfigurieren Sie signingConfigs in Gradle und aktivieren Sie Play App Signing beim ersten Upload. Halten Sie den Keystore aus git heraus, zum Beispiel im per .gitignore ausgeschlossenen release/keys/.

iOS-Signierung ohne Inhaberzugriff

Unter iOS erfordern das Signieren der App und das Hochladen unterschiedliche Dinge, und beides liegt meist beim Account Holder oder einem Admin. appship baut und signiert auch hier nicht für Sie. Es prüft die Dateien, die Sie erhalten haben, installiert sie und reicht die Signier-Einstellungen an Ihren Build-Befehl weiter.

Beim Inhaber anfordern

  • Ein Apple Distribution-Zertifikat als .p12, aus Keychain Access mit Passwort exportiert. Es muss den privaten Schlüssel enthalten.
  • Ein App Store-Provisioning-Profil (.mobileprovision) für jede Bundle-ID, einschließlich App-Extensions.
  • Optional einen Team-API-Schlüssel: .p8, Key ID und Issuer ID.

Um zu vermeiden, dass ein privater Schlüssel weitergegeben wird, erstellen Sie auf Ihrem eigenen Mac eine Certificate Signing Request und lassen den Inhaber das Zertifikat daraus ausstellen. Dann verlässt der private Schlüssel Ihren Rechner nie, und Sie brauchen die .p12 nicht.

Konfigurieren und installieren

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # Profile installieren, die .p12 importieren
appship build --ios
appship doctor                                    # Profile, Keychain und die gebaute .ipa prüfen
appship upload --ios

Das Passwort der .p12 wird nie in release.yml gespeichert; übergeben Sie es in APPSHIP_P12_PASSWORD. Der Build-Befehl erhält $APPSHIP_EXPORT_OPTIONS (eine generierte ExportOptions.plist), $APPSHIP_IOS_BUNDLE_ID und $APPSHIP_IOS_TEAM_ID. Für fastlane gym verwenden Sie --export_options "$APPSHIP_EXPORT_OPTIONS". Die plist steuert nur den Export-Schritt; bei manueller Signierung schalten Sie im Xcode-Projekt außerdem die automatische Signierung aus, damit der Archive-Schritt dasselbe Profil verwendet.

Was doctor prüft

  • Jedes Profil ist ein iOS-App Store-Profil, nicht abgelaufen (Warnung unter 30 Tagen), stammt vom Team in ios.team_id und deckt ios.bundle_id ab.
  • Die .p12 existiert und ist nicht für alle lesbar, und ein passendes Zertifikat mit privatem Schlüssel liegt in der Keychain (nur macOS).
  • Die gebaute .ipa ist für die richtige Bundle-ID signiert, mit einem gültigen Profil aus ios.signing.profiles.
  • build_command verwendet tatsächlich $APPSHIP_EXPORT_OPTIONS.

Kein Team-API-Schlüssel

  • Individueller Schlüssel: in App Store Connect unter Integrations → Individual Keys. Er hat keine Issuer ID, lassen Sie issuer_id daher leer: appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. Er trägt die Berechtigungen Ihrer eigenen Rolle, und ein Admin kann die Funktion abschalten. Noch nicht mit einem echten Konto verifiziert.
  • Gar kein Schlüssel: signieren und bauen Sie auf dieselbe Weise und laden Sie die .ipa dann mit Transporter oder Xcode → Organizer → Distribute App hoch. doctor prüft die Datei vorher trotzdem. appship lädt nicht mit einer Apple-ID hoch, da das eine interaktive 2FA erfordert.

In der CI

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

Dadurch wird eine eigene Keychain angelegt, sodass die Login-Keychain des Runners unangetastet bleibt. Profile und Zertifikate laufen nach etwa einem Jahr ab; doctor warnt 30 Tage vorher.

Rollen unterscheiden sich in dem, was sie dürfen; sehen Sie in die Rollentabelle in der App-Store-Connect-Hilfe. Die Bildschirme von Apple ändern sich, betrachten Sie die Schritte daher als Stand 09/2026.

Woher Schlüssel gelesen werden

Für jeden Wert gewinnt die erste gefundene Quelle. Sie können sie mischen, zum Beispiel ein Profil auf Ihrem Rechner und Umgebungsvariablen in der CI.

  1. Umgebungsvariablen: APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH oder APPSHIP_ASC_KEY (Inhalt, Klartext oder base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH oder APPSHIP_PLAY_JSON sowie APPSHIP_PROFILE.
  2. release/release.yml: Pfade zu Dateien im per .gitignore ausgeschlossenen release/keys/. Key ID und Issuer ID sind keine Geheimnisse und dürfen committet werden.
  3. Ein Profil: credentials.profile: my-company, das auf ~/.appship/credentials/my-company/ verweist.
release/release.yml, ohne Profil
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # optional
  android:
    json_key_path: release/keys/play-service-account.json

Wenn ein Schlüssel committet wurde

  1. Widerrufen Sie ihn sofort. iOS: App Store Connect → Integrations → Revoke. Android: Cloud Console → das Dienstkonto → Keys → Delete.
  2. Erstellen Sie einen neuen Schlüssel und aktualisieren Sie Ihr Profil oder die CI-Secrets.
  3. Führen Sie git rm --cached <file> aus. Der Schlüssel bleibt in der git-Historie, weshalb der Widerruf der entscheidende Schritt ist.
