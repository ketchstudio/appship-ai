Ajoutez appship à votre projet

D’une app qui n’a jamais été sur les stores à un build en App Review. Comptez environ une heure la première fois, dont l’essentiel passé dans les consoles Apple et Google à récupérer les clés.

Version préliminaire. La v0.1.0 est couverte par des tests et des dry-runs, mais n’a pas encore été exécutée sur les vrais stores. Chaque commande qui écrit sur un store accepte --dry-run ; commencez par des commandes en lecture seule comme appship status.

1Prérequis

2Installation

Installez appship une fois par machine, de façon globale. Rien n’est ajouté au package.json de votre app.

terminal
npm i -g appship-ai
appship --version

Le paquet s’appelle appship-ai et installe la commande appship. Pour l’essayer sans l’installer, lancez npx appship-ai --help.

3Obtenir les clés des stores

Vous le faites une seule fois par compte développeur, pas par projet. Les deux clés peuvent publier des builds en votre nom : ne les commitez jamais dans git.

iOS : clé d’API App Store Connect

  1. Dans App Store Connect, ouvrez Users and Access → Integrations → App Store Connect API.
  2. Sous Team Keys, cliquez sur +. Nommez-la appship et donnez-lui le rôle App Manager.
  3. Téléchargez AuthKey_XXXXXXXXXX.p8. Apple ne permet de le télécharger qu’une seule fois.
  4. Notez le Key ID (10 caractères, aussi présent dans le nom du fichier) et l’Issuer ID (l’UUID au-dessus du tableau des clés).

Seuls un Account Holder ou un Admin peuvent créer des Team Keys. Si ce n’est pas votre cas, demandez au propriétaire de vous envoyer la clé, ou consultez Signature iOS sans accès propriétaire pour une clé individuelle.

Un Apple ID (e-mail) est facultatif. Il n’est nécessaire que pour créer la fiche de l’app et envoyer les réponses App Privacy, car la clé d’API d’Apple ne permet ni l’un ni l’autre. Il exige la 2FA, donc il ne fonctionne jamais en CI.

Android : compte de service Google Play

  1. Dans Google Cloud Console, choisissez un projet et activez la Google Play Android Developer API.
  2. Allez dans IAM & Admin → Service Accounts → Create service account. Aucun rôle GCP n’est nécessaire.
  3. Ouvrez le compte, puis Keys → Add key → JSON pour télécharger le fichier de clé.
  4. Dans Play Console, allez dans Users and permissions → Invite new users et invitez le client_email du JSON. Accordez Release apps to testing tracks, Release to production et Manage store presence.
  5. Attendez quelques minutes que les permissions s’appliquent. Sur un nouveau compte, cela peut prendre jusqu’à 24 heures.

Les enregistrer dans un profil

Un profil copie les clés dans ~/.appship/credentials/<name>/ avec les droits 600, afin que tous les projets de cette machine puissent les partager. Lancez la commande sans options pour être guidé pas à pas.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4Configurer le projet

Lancez init depuis la racine du dépôt de votre app.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init détecte les projets Flutter, React Native, Cocos Creator ou natifs, lit votre bundle id et votre nom de paquet, puis renseigne la commande de build et le chemin de l’artefact. Il crée ce dossier et ajoute release/keys/* et release/.appship/ au .gitignore :

project layout
my-app/
└── release/
    ├── release.yml            # ids, artefacts, commandes de build, tracks, identifiants
    ├── questionnaire.yml      # réponses aux questions des stores
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # ignoré par git ; seulement si vous n’utilisez pas de profil
    └── .appship/              # ignoré par git ; fichiers temporaires pour fastlane

Ouvrez release/release.yml et vérifiez artifact et build_command pour chaque plateforme. Pour une app Flutter, cela ressemble à ceci :

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # publier dès qu’Apple approuve
    phased_release: false      # déploiement progressif sur 7 jours
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # draft tant que l’app n’est pas publiée
  rollout: 1                   # 0.2 = déploiement progressif à 20 %
credentials:
  profile: my-company

Commitez tout le dossier release/ sauf keys/ et .appship/. Votre dépôt ne reçoit aucun Fastfile : la logique de release reste dans appship, donc mettre à jour appship met à jour tous les projets.

5Renseigner la fiche

Si l’app est déjà en ligne, récupérez la fiche actuelle au lieu de la saisir :

terminal
appship metadata pull

Sinon, remplacez chaque TODO dans ces fichiers :

  • release/questionnaire.yml : classification par âge, conformité à l’export, droits sur le contenu, contact pour la review, App Privacy et réponses App content d’Android.
  • Textes : release/ios/metadata/<locale>/*.txt et release/android/metadata/<locale>/*.txt.
  • Notes de version par langue : un dossier par locale. Voir Langues et notes de version ci-dessous.
  • Captures d’écran iOS dans release/ios/screenshots/<locale>/ : au moins un jeu iPhone 6.9" (1320×2868) ou 6.5" (1284×2778).
  • Images Android dans release/android/metadata/<locale>/images/ : icon.png 512×512, featureGraphic.png 1024×500 et au moins 2 images dans phoneScreenshots/.

Langues et notes de version

Les deux stores acceptent un texte « Nouveautés » distinct pour chaque langue. Chaque langue est un dossier, et chaque dossier contient ses propres notes de version :

StoreFichier, un par dossier de localeMax
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 caractères
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 caractères

Pour ajouter une langue :

  1. Listez-la dans release.yml. La liste est facultative ; sans elle, appship utilise tous les dossiers qu’il trouve. iOS et Android utilisent des codes de locale différents, donc chaque plateforme a sa propre liste :
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # les codes Play diffèrent, p. ex. zh-CN ici, zh-Hans sur iOS
  2. Créez le dossier, par exemple release/ios/metadata/vi/, et renseignez les fichiers requis : name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt et release_notes.txt sur iOS ; title.txt, short_description.txt, full_description.txt et changelogs/default.txt sur Android.
  3. Ajoutez les captures d’écran iOS dans release/ios/screenshots/<locale>/. Pour Android, activez d’abord la langue dans Play Console.
  4. Lancez appship doctor. Une locale listée sans dossier est une erreur. Un dossier non listé est un avertissement, car il est tout de même envoyé au store.

À savoir :

  • Vous n’avez pas besoin d’ajouter la langue dans App Store Connect au préalable. Elle est créée lors de l’envoi des métadonnées.
  • Laissez release_notes.txt vide pour la toute première version d’une app. Apple n’accepte pas de notes de version pour la version 1.0.
  • Une locale sans notes de version affiche un « Nouveautés » vide dans cette langue. doctor avertit quand certaines locales ont des notes et d’autres non.
  • Les noms de dossier iOS doivent correspondre à l’un des codes d’Apple, comme en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans ou zh-Hant. doctor rejette tout le reste, par exemple zh-CN.
  • Le dossier partagé default de fastlane n’est pas encore pris en charge.

Langues suggérées

Vous ne savez pas quelles langues ajouter ensuite ? appship en suggère six à large audience : l’espagnol (Espagne et Amérique latine), le portugais brésilien, l’allemand, le français, le japonais et le coréen. Les deux stores utilisent des codes différents :

Langueid --localesDossier iOSDossier Android
Espagnol, Espagneeses-ESes-ES
Espagnol, Amérique latineeses-MXes-419
Portugais, Brésilpt-BRpt-BRpt-BR
Allemanddede-DEde-DE
Françaisfrfr-FRfr-FR
Japonaisjajaja-JP
Coréenkokoko-KR
  • Créez les dossiers lors de la configuration d’un projet : appship init --locales preset pour les six, ou --locales es,ja pour certaines. La commande écrit locales pour chaque plateforme avec les bons codes et crée des fichiers de fiche remplis de TODO à traduire. doctor échoue tant que chaque TODO n’est pas remplacé.
  • Pour un projet existant, ajoutez les dossiers à la main avec les codes ci-dessus (init --force réécrirait release.yml).
  • Ne gardez que la variante d’espagnol que vous rédigerez réellement. es-MX sur iOS et es-419 sur Play couvrent toute l’Amérique latine.
  • Les limites des stores comptent des caractères, pas des octets ni des mots. Le texte japonais et coréen est en général plus court que l’anglais ; l’allemand et le français sont plus longs et atteignent souvent la limite de 30 caractères du titre.
  • Activez chaque langue dans Play Console avant l’envoi. doctor avertit quand un dossier Android n’est pas un code de langue Play et propose la correction, par exemple ja devrait être ja-JP.
  • Le skill release-notes connaît les conventions de chaque langue : tutoiement ou vouvoiement, variantes régionales, ponctuation pleine chasse japonaise et espacement français avant ? ! : ;.

Rédiger les notes de version avec un agent de code IA

appship init installe un skill, release-notes, pour votre agent de code IA (Claude Code, Codex ou Antigravity) : dans .claude/skills/ pour Claude Code, dans .agents/skills/ pour Codex et Antigravity. Avant une release, demandez à l’agent de « rédiger les notes de version pour cette version » (ou lancez /release-notes dans Claude Code, $release-notes dans Codex). Il va :

  1. Lire release.yml et les dossiers de locales.
  2. Lire git log depuis le dernier tag, ainsi que CHANGELOG.md si vous en avez un.
  3. Rédiger des notes courtes, orientées utilisateur, dans votre langue principale, puis les traduire dans toutes les autres locales.
  4. Respecter les limites des stores, écrire les fichiers, puis lancer appship doctor.

Les notes restent de simples fichiers, vous pouvez donc les relire et les modifier. Le skill demande avant d’écraser un texte existant et n’envoie jamais rien à un store.

Captures d’écran et déclarations des stores avec un agent IA

init installe deux autres skills à côté. Comme release-notes, ils se contentent d’écrire des fichiers dans release/ et de lancer appship doctor, et vous laissent l’envoi vers les stores.

  • store-screenshots : prépare les captures avec vous, les réalise depuis le simulateur iOS ou un émulateur Android, ajoute un titre traduit pour chaque langue et génère chaque image dans une taille acceptée par chaque store (iPhone 6.9" 1320×2868, iPad 13" si l’app tourne sur iPad, Play 1080×1920), ainsi que l’icône et la feature graphic de Play.
  • app-content : remplit release/questionnaire.yml (classification par âge, App Privacy, conformité à l’export, Data safety, classification du contenu, public cible, publicités, accès à l’app) à partir de vos dépendances, permissions et code, vous demande ce que le code ne peut pas montrer, et garde les réponses cohérentes entre les deux stores.
AgentDossier des skillsComment le lancer
Claude Code.claude/skills//store-screenshots
Codex.agents/skills/$store-screenshots ou /skills
Antigravity.agents/skills/demandez « use the store-screenshots skill »

appship n’appelle jamais d’IA lui-même. Ouvrez l’agent à la racine du projet, connecté avec votre propre compte, et approuvez les commandes qu’il demande à lancer.

Choisissez les agents lors de init, ou installez et mettez à jour les skills plus tard, par exemple après une mise à jour d’appship :

terminal
appship init --agents all             # skills pour Claude Code, Codex et Antigravity
appship skills                        # les skills de chaque agent
appship skills add --agent codex      # installe pour Codex / Antigravity (.agents/skills/)
appship skills add --force            # les remplace par ceux de cette version

6Vérifier avec doctor

doctor vérifie les outils, la configuration, les clés, les artefacts, les limites de caractères, les tailles d’image et les textes provisoires, et échoue si un fichier de clé est suivi par git. Répétez jusqu’à ce qu’il n’y ait plus de ✗. Un ! est un avertissement et ne bloque pas une release.

appship doctor
▸ Security
  ✓ No key files tracked by git
  ✓ .gitignore protects release/keys/
▸ iOS · store listing
  ✗ ios/metadata/en-US/subtitle.txt is 34 characters (max 30)
▸ Android · store listing
  ✓ Metadata OK for en-US

  ✗ 1 error(s), 0 warning(s)

7Première release

terminal
appship build
appship first-release --create-app
  • iOS : crée l’app dans App Store Connect (nécessite l’Apple ID et peut demander un code 2FA), puis envoie la fiche, les captures d’écran, la classification par âge, les infos de review et App Privacy.
  • Android : Google Play n’a pas d’API pour créer une app, donc appship affiche les étapes à la place.
  • Les deux écrivent release/CHECKLIST.md : les étapes de console à faire à la main, avec vos réponses de questionnaire.yml prêtes à copier.

Sur Google Play, suivez la checklist pour :

  1. Créer l’app dans Play Console.
  2. Inviter le compte de service sur l’app.
  3. Envoyer le premier .aab à la main dans Internal testing.
  4. Remplir la section App content.

Tant que l’app Android n’a jamais été publiée, définissez release_status: draft dans release.yml. Les nouveaux comptes développeur personnels doivent aussi mener un test fermé avec 12 testeurs pendant 14 jours avant la production.

Terminez ensuite la première release :

terminal
appship metadata --android
appship upload
appship submit

8Chaque release suivante

Incrémentez la version et le numéro de build dans votre projet, puis :

terminal
# demandez à votre agent IA de rédiger les notes de version (voir Langues et notes de version)
appship upload --build   # build, puis TestFlight + track Google Play (internal par défaut)
# testez sur TestFlight / le track internal
appship submit           # iOS : App Review · Android : promotion en production
appship status           # état de la review et versions sur les deux stores

Pour un déploiement progressif sur Android :

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

Chaque commande qui écrit sur un store demande d’abord une confirmation. Ajoutez --dry-run pour voir exactement ce qui serait envoyé.

9L’exécuter en CI

En CI, les clés proviennent des secrets via les variables d’environnement APPSHIP_*, et chaque commande d’écriture exige --yes. Ajoutez ces secrets de dépôt (dans GitHub : Settings → Secrets and variables → Actions) :

SecretValeur
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYSortie de base64 -i AuthKey_XXX.p8
APPSHIP_PLAY_JSONSortie de base64 -i play-service-account.json
Secrets de signatureSelon votre méthode de signature, par exemple MATCH_PASSWORD pour fastlane match, ou un keystore Android en base64

Les étapes de release d’un workflow GitHub Actions :

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # les builds iOS nécessitent macOS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...votre toolchain, fastlane et la configuration de la signature...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Ajoutez votre propre configuration Flutter, votre étape de signature et, si vous voulez un déclenchement manuel pour submit, une entrée workflow_dispatch comme celle ci-dessus.

  • Créer l’app iOS et envoyer App Privacy nécessitent l’Apple ID avec 2FA. Faites-le une fois sur votre machine, pas en CI.
  • Pour figer une version de fastlane, utilisez un Gemfile et définissez APPSHIP_FASTLANE="bundle exec fastlane".
  • Testez le pipeline de bout en bout avec --dry-run avant de le laisser envoyer quoi que ce soit.

Référence

Signature

appship ne compile ni ne signe votre app. Il exécute votre build_command et récupère l’artefact signé.

  • iOS : la configuration la plus simple est la signature automatique dans Xcode (Signing & Capabilities). Pour les équipes et la CI, utilisez fastlane match.
  • Android : créez un keystore d’upload, configurez signingConfigs dans Gradle et activez Play App Signing dès le premier envoi. Gardez le keystore hors de git, par exemple dans release/keys/, ignoré par git.

Signature iOS sans accès propriétaire

Sur iOS, signer l’app et l’envoyer ne demandent pas les mêmes éléments, et les deux sont généralement détenus par l’Account Holder ou un Admin. appship ne compile et ne signe toujours pas à votre place. Il audite les fichiers que l’on vous a remis, les installe et transmet la configuration de signature à votre commande de build.

Votre situationSigner avecEnvoyer avec
Account Holder ou AdminSignature automatique, ou fastlane matchClé d’API d’équipe
Le propriétaire a envoyé les fichiers de signature et une clé d’API d’équipeFichiers ios.signingClé d’API d’équipe
Le propriétaire a envoyé les fichiers de signature, sans clé d’APIFichiers ios.signingVotre propre clé d’API individuelle
Aucune clé d’APIFichiers ios.signingTransporter ou Xcode Organizer, à la main

À demander au propriétaire

  • Un certificat Apple Distribution au format .p12, exporté depuis Keychain Access avec un mot de passe. Il doit inclure la clé privée.
  • Un profil de provisionnement App Store (.mobileprovision) pour chaque bundle id, extensions d’app comprises.
  • Éventuellement une clé d’API d’équipe : .p8, Key ID et Issuer ID.

Pour éviter de faire circuler une clé privée, créez une demande de signature de certificat (CSR) sur votre propre Mac et demandez au propriétaire d’émettre le certificat à partir de celle-ci. Ainsi, la clé privée ne quitte jamais votre machine et vous n’avez pas besoin du .p12.

Configurer et installer

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # installe les profils, importe le .p12
appship build --ios
appship doctor                                    # audite les profils, le trousseau et le .ipa compilé
appship upload --ios

Le mot de passe du .p12 n’est jamais stocké dans release.yml ; transmettez-le via APPSHIP_P12_PASSWORD. La commande de build reçoit $APPSHIP_EXPORT_OPTIONS (un ExportOptions.plist généré), $APPSHIP_IOS_BUNDLE_ID et $APPSHIP_IOS_TEAM_ID. Pour fastlane gym, utilisez --export_options "$APPSHIP_EXPORT_OPTIONS". Le plist ne contrôle que l’étape d’export ; avec la signature manuelle, désactivez aussi la signature automatique dans le projet Xcode afin que l’étape d’archive utilise le même profil.

Ce que doctor vérifie

  • Chaque profil est un profil iOS App Store, non expiré (avertissement sous 30 jours), provenant de l’équipe de ios.team_id, et couvre ios.bundle_id.
  • Le .p12 existe et n’est pas lisible par tous, et un certificat correspondant avec sa clé privée se trouve dans le trousseau (macOS uniquement).
  • Le .ipa compilé est signé pour le bon bundle id, avec un profil valide de ios.signing.profiles.
  • build_command utilise bien $APPSHIP_EXPORT_OPTIONS.

Sans clé d’API d’équipe

  • Clé individuelle : dans App Store Connect, Integrations → Individual Keys. Elle n’a pas d’Issuer ID, laissez donc issuer_id vide : appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. Elle porte les permissions de votre propre rôle, et un Admin peut désactiver cette fonctionnalité. Pas encore vérifié sur un compte réel.
  • Aucune clé : signez et compilez de la même façon, puis envoyez le .ipa avec Transporter ou Xcode → Organizer → Distribute App. doctor audite tout de même le fichier au préalable. appship n’envoie pas avec un Apple ID, car cela exige une 2FA interactive.

En CI

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

Cela crée un trousseau dédié, de sorte que le trousseau de session du runner reste intact. Les profils et certificats expirent au bout d’un an environ ; doctor avertit 30 jours avant.

Les rôles diffèrent quant à ce qu’ils peuvent faire ; consultez le tableau des rôles dans l’aide d’App Store Connect. Les écrans d’Apple changent, considérez donc ces étapes comme valables en 09/2026.

D’où sont lues les clés

Pour chaque valeur, la première source trouvée l’emporte. Vous pouvez les combiner, par exemple un profil sur votre machine et des variables d’environnement en CI.

  1. Variables d’environnement : APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH ou APPSHIP_ASC_KEY (contenu, brut ou en base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH ou APPSHIP_PLAY_JSON, et APPSHIP_PROFILE.
  2. release/release.yml : chemins vers des fichiers dans release/keys/, ignoré par git. Le Key ID et l’Issuer ID ne sont pas des secrets et peuvent être commités.
  3. Un profil : credentials.profile: my-company, pointant vers ~/.appship/credentials/my-company/.
release/release.yml, sans profil
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # facultatif
  android:
    json_key_path: release/keys/play-service-account.json

Si une clé est commitée

  1. Révoquez-la immédiatement. iOS : App Store Connect → Integrations → Revoke. Android : Cloud Console → le compte de service → Keys → Delete.
  2. Créez une nouvelle clé et mettez à jour votre profil ou vos secrets de CI.
  3. Lancez git rm --cached <file>. La clé reste dans l’historique git, c’est pourquoi la révoquer est l’étape qui compte.
