Guia de integração · v0.2.0

Adicione o appship ao seu projeto

De um app que nunca esteve nas lojas a um build em análise. Reserve cerca de uma hora na primeira vez, a maior parte gasta nos consoles da Apple e do Google para obter as chaves.

Versão inicial. A v0.2.0 é coberta por testes e dry-runs, mas ainda não foi executada nas lojas reais. Todo comando que grava em uma loja aceita --dry-run; comece com comandos somente leitura, como appship status.

1Requisitos

Você precisa deObservações
Node.js 22 ou mais recenteO appship é um pacote npm.
fastlaneO appship executa o fastlane em toda chamada às lojas. Instale-o da forma que a documentação do fastlane recomenda para a sua máquina.
macOS com XcodeSomente para builds e uploads de iOS. Projetos só Android também funcionam no Linux.
Apple Developer Program99 USD por ano.
Conta do Google Play Console25 USD, pagamento único.
Um app que gera um release assinadoO appship não assina por você. Veja Assinatura.

2Instalação

Instale o appship uma vez por máquina, de forma global. Nada é adicionado ao package.json do seu app.

terminal
npm i -g appship-ai
appship --version

O pacote se chama appship-ai e instala o comando appship. Para testar sem instalar, execute npx appship-ai --help.

3Obter as chaves das lojas

Você faz isso uma vez por conta de desenvolvedor, não por projeto. As duas chaves podem publicar builds em seu nome, então nunca as envie ao git.

iOS: chave da API do App Store Connect

  1. No App Store Connect, abra Users and Access → Integrations → App Store Connect API.
  2. Em Team Keys, clique em +. Dê a ela o nome appship e a função App Manager.
  3. Baixe o AuthKey_XXXXXXXXXX.p8. A Apple permite baixá-lo apenas uma vez.
  4. Anote o Key ID (10 caracteres, também no nome do arquivo) e o Issuer ID (o UUID acima da tabela de chaves).

Team Keys só podem ser criadas por um Account Holder ou Admin. Se não for você, peça ao proprietário que envie a chave, ou veja Assinatura iOS sem acesso de proprietário para usar uma chave individual.

Um Apple ID (e-mail) é opcional. Ele só é necessário para criar o registro do app e enviar as respostas de App Privacy, porque a chave de API da Apple não faz nenhuma das duas coisas. Ele exige 2FA, então nunca funciona no CI.

Android: conta de serviço do Google Play

  1. No Google Cloud Console, escolha um projeto e ative a Google Play Android Developer API.
  2. Acesse IAM & Admin → Service Accounts → Create service account. Ela não precisa de nenhuma função do GCP.
  3. Abra a conta e vá em Keys → Add key → JSON para baixar o arquivo da chave.
  4. No Play Console, acesse Users and permissions → Invite new users e convide o client_email do JSON. Conceda Release apps to testing tracks, Release to production e Manage store presence.
  5. Aguarde alguns minutos para as permissões entrarem em vigor. Em uma conta nova, pode levar até 24 horas.

Salve como um perfil

Um perfil copia as chaves para ~/.appship/credentials/<name>/ com permissão 600, para que todos os projetos desta máquina possam compartilhá-las. Execute sem flags para ser guiado passo a passo.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4Configurar o projeto

Execute o init na raiz do repositório do seu app.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init detecta projetos Flutter, React Native, Cocos Creator ou nativos, lê o seu bundle id e o nome do pacote, e preenche o comando de build e o caminho do artefato. Ele cria esta pasta e adiciona release/keys/* e release/.appship/ ao .gitignore:

estrutura do projeto
my-app/
└── release/
    ├── release.yml            # ids, artefatos, comandos de build, tracks, credenciais
    ├── questionnaire.yml      # respostas às perguntas das lojas
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # no gitignore; só se você não usar um perfil
    └── .appship/              # no gitignore; arquivos temporários do fastlane

Abra o release/release.yml e confira artifact e build_command de cada plataforma. Em um app Flutter, fica assim:

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # publica assim que a Apple aprovar
    phased_release: false      # lançamento gradual em 7 dias
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # draft enquanto o app não está publicado
  rollout: 1                   # 0.2 = lançamento gradual para 20%
credentials:
  profile: my-company

Faça commit de toda a pasta release/, exceto keys/ e .appship/. Seu repositório não recebe nenhum Fastfile: a lógica de release fica no appship, então atualizar o appship atualiza todos os projetos.

5Preencher a ficha do app

Se o app já está publicado, baixe a ficha atual em vez de digitá-la:

terminal
appship metadata pull

Caso contrário, substitua cada TODO nestes arquivos:

  • release/questionnaire.yml: classificação etária, conformidade de exportação, direitos de conteúdo, contato do revisor, App Privacy e as respostas de conteúdo do app no Android.
  • Texto: release/ios/metadata/<locale>/*.txt e release/android/metadata/<locale>/*.txt.
  • Notas de versão por idioma: uma pasta por locale. Veja Idiomas e notas de versão abaixo.
  • Capturas de tela do iOS em release/ios/screenshots/<locale>/: pelo menos um conjunto de iPhone 6.9" (1320×2868) ou 6.5" (1284×2778).
  • Imagens do Android em release/android/metadata/<locale>/images/: icon.png 512×512, featureGraphic.png 1024×500, e pelo menos 2 imagens em phoneScreenshots/.

Idiomas e notas de versão

As duas lojas aceitam um texto de "Novidades" separado para cada idioma. Cada idioma é uma pasta, e cada pasta guarda as suas próprias notas de versão:

LojaArquivo, um por pasta de localeMáx.
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 caracteres
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 caracteres

Para adicionar um idioma:

  1. Liste-o no release.yml. A lista é opcional; sem ela, o appship usa todas as pastas que encontrar. iOS e Android usam códigos de locale diferentes, então cada plataforma tem a sua própria lista:
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # os códigos do Play diferem, ex.: zh-CN aqui, zh-Hans no iOS
  2. Crie a pasta, por exemplo release/ios/metadata/vi/, e preencha os arquivos obrigatórios: name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt e release_notes.txt no iOS; title.txt, short_description.txt, full_description.txt e changelogs/default.txt no Android.
  3. Adicione as capturas de tela do iOS em release/ios/screenshots/<locale>/. No Android, ative o idioma no Play Console antes.
  4. Execute appship doctor. Um locale listado sem pasta é um erro. Uma pasta que não está na lista é um aviso, porque ela ainda é enviada à loja.

Vale saber:

  • Você não precisa adicionar o idioma no App Store Connect antes. Ele é criado quando os metadados são enviados.
  • Deixe o release_notes.txt vazio na primeira versão de um app. A Apple não aceita notas de versão na versão 1.0.
  • Um locale sem notas de versão mostra "Novidades" vazio nesse idioma. doctor avisa quando alguns locales têm notas e outros não.
  • Os nomes das pastas do iOS devem ser um dos códigos da Apple, como en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans ou zh-Hant. doctor rejeita qualquer outro, por exemplo zh-CN.
  • A pasta default compartilhada do fastlane ainda não é suportada.

Idiomas sugeridos

Não sabe quais idiomas adicionar em seguida? O appship sugere seis com grande público: espanhol (Espanha e América Latina), português do Brasil, alemão, francês, japonês e coreano. As duas lojas usam códigos diferentes:

Idioma--locales idPasta iOSPasta Android
Espanhol, Espanhaeses-ESes-ES
Espanhol, América Latinaeses-MXes-419
Português, Brasilpt-BRpt-BRpt-BR
Alemãodede-DEde-DE
Francêsfrfr-FRfr-FR
Japonêsjajaja-JP
Coreanokokoko-KR
  • Crie as pastas ao configurar um projeto: appship init --locales preset para as seis, ou --locales es,ja para algumas. Ele grava locales em cada plataforma com os códigos certos e cria arquivos de ficha preenchidos com TODO para você traduzir. doctor falha até que todo TODO seja substituído.
  • Em um projeto que já existe, adicione as pastas à mão com os códigos acima (init --force reescreveria o release.yml).
  • Mantenha apenas a variante de espanhol que você realmente vai escrever. es-MX no iOS e es-419 no Play cobrem toda a América Latina.
  • Os limites das lojas contam caracteres, não bytes nem palavras. Textos em japonês e coreano costumam ser mais curtos que em inglês; alemão e francês são mais longos e frequentemente atingem o limite de 30 caracteres do título.
  • Ative cada idioma no Play Console antes de enviar. doctor avisa sobre uma pasta Android que não é um código de idioma do Play e sugere a correção, por exemplo ja deve ser ja-JP.
  • The release-notes conhece as convenções de cada idioma: tratamento formal ou informal, variantes regionais, pontuação de largura total do japonês e o espaçamento do francês antes de ? ! : ;.

Escreva as notas de versão com um agente de programação com IA

appship init instala uma skill, release-notes, para o seu agente de programação com IA (Claude Code, Codex ou Antigravity): em .claude/skills/ para o Claude Code e em .agents/skills/ para o Codex e o Antigravity. Antes de um lançamento, peça ao agente para "escrever as notas de versão desta versão" (ou execute /release-notes no Claude Code ou $release-notes no Codex). Ele vai:

  1. Ler o release.yml e as pastas de locale.
  2. Ler o git log desde a última tag e o CHANGELOG.md, se você tiver um.
  3. Escrever notas curtas, voltadas ao usuário, no seu idioma principal e traduzi-las para todos os outros locales.
  4. Respeitar os limites das lojas, gravar os arquivos e então executar appship doctor.

As notas continuam sendo arquivos simples, então você pode revisá-las e editá-las. A skill pergunta antes de sobrescrever textos que já existem e nunca envia nada a uma loja.

Capturas de tela e declarações das lojas com um agente de IA

O init instala mais duas skills ao lado dela. Assim como a release-notes, elas só gravam arquivos em release/, executam appship doctor e deixam o envio às lojas com você.

  • store-screenshots: planeja as capturas com você, faz as capturas no Simulador do iOS ou em um emulador Android, adiciona um título traduzido para cada idioma e gera cada imagem em um tamanho aceito por cada loja (iPhone 6.9" 1320×2868, iPad 13" quando o app roda no iPad, Play 1080×1920), além do ícone e do gráfico de recursos do Play.
  • app-content: preenche o release/questionnaire.yml (classificação etária, App Privacy, conformidade de exportação, Segurança dos dados, classificação do conteúdo, público-alvo, anúncios, acesso ao app) a partir das suas dependências, permissões e código, pergunta a você o que o código não consegue mostrar e mantém as respostas consistentes entre as duas lojas.
AgentePasta das skillsComo executar
Claude Code.claude/skills//store-screenshots
Codex.agents/skills/$store-screenshots ou /skills
Antigravity.agents/skills/peça "use the store-screenshots skill"

O appship nunca chama uma IA por conta própria. Abra o agente na raiz do projeto, conectado com a sua própria conta, e aprove os comandos que ele pedir para executar.

Escolha os agentes ao executar o init, ou instale e atualize as skills depois, por exemplo após atualizar o appship:

terminal
appship init --agents all             # skills para Claude Code, Codex e Antigravity
appship skills                        # quais skills cada agente tem
appship skills add --agent codex      # instala para Codex / Antigravity (.agents/skills/)
appship skills add --force            # substitui pelas desta versão

6Verificar com o doctor

doctor verifica ferramentas, configuração, chaves, artefatos, limites de caracteres, tamanhos de imagem e textos de placeholder, e falha se algum arquivo de chave estiver rastreado pelo git. Repita até não haver nenhum ✗. Um ! é um aviso e não bloqueia um lançamento.

appship doctor
▸ Security
  ✓ Nenhum arquivo de chave rastreado pelo git
  ✓ .gitignore protege release/keys/
▸ iOS · ficha na loja
  ✗ ios/metadata/en-US/subtitle.txt tem 34 caracteres (máx. 30)
▸ Android · ficha na loja
  ✓ Metadados OK para en-US

  ✗ 1 erro(s), 0 aviso(s)

7Primeiro lançamento

terminal
appship build
appship first-release --create-app
  • iOS: cria o app no App Store Connect (precisa do Apple ID e pode pedir um código 2FA) e depois envia a ficha, as capturas de tela, a classificação etária, as informações de revisão e o App Privacy.
  • Android: o Google Play não tem API para criar um app, então o appship imprime os passos no lugar.
  • Ambos gravam o release/CHECKLIST.md: os passos do console que precisam ser feitos à mão, com as suas respostas do questionnaire.yml prontas para copiar.

No Google Play, siga o checklist para:

  1. Criar o app no Play Console.
  2. Convidar a conta de serviço para o app.
  3. Enviar o primeiro .aab à mão para o Internal testing.
  4. Preencher a seção App content.

Enquanto o app Android nunca tiver sido publicado, defina release_status: draft no release.yml. Contas pessoais de desenvolvedor novas também precisam de um teste fechado com 12 testadores por 14 dias antes da produção.

Depois, conclua o primeiro lançamento:

terminal
appship metadata --android
appship upload
appship submit

8Todos os lançamentos seguintes

Aumente a versão e o número do build no seu projeto e depois execute:

terminal
# peça ao seu agente de IA para escrever as notas de versão (veja Idiomas e notas de versão)
appship upload --build   # faz o build e envia ao TestFlight + track do Google Play (internal por padrão)
# teste no TestFlight / na track internal
appship submit           # iOS: App Review · Android: promove para produção
appship status           # estado da revisão e versões nas duas lojas

Para um lançamento gradual no Android:

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

Todo comando que grava em uma loja pede confirmação antes. Adicione --dry-run para ver exatamente o que seria enviado.

9Execute no CI

No CI, as chaves vêm de secrets por meio das variáveis de ambiente APPSHIP_*, e todo comando de gravação precisa de --yes. Adicione estes secrets ao repositório (no GitHub: Settings → Secrets and variables → Actions):

SecretValor
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYSaída de base64 -i AuthKey_XXX.p8
APPSHIP_PLAY_JSONSaída de base64 -i play-service-account.json
Secrets de assinaturaDepende de como você assina, por exemplo MATCH_PASSWORD para o fastlane match, ou um keystore Android em base64

Os passos de release de um workflow do GitHub Actions:

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # builds de iOS precisam de macOS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...sua toolchain, fastlane e configuração de assinatura...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Adicione a sua própria configuração do Flutter, o passo de assinatura e, se quiser um gatilho manual para o submit, uma entrada workflow_dispatch como a acima.

  • Criar o app iOS e enviar o App Privacy exigem o Apple ID com 2FA. Faça isso uma vez na sua máquina, não no CI.
  • Para fixar uma versão do fastlane, use um Gemfile e defina APPSHIP_FASTLANE="bundle exec fastlane".
  • Teste o pipeline de ponta a ponta com --dry-run antes de deixá-lo enviar qualquer coisa.

Referência

Assinatura

O appship não faz o build nem assina o seu app. Ele executa o seu build_command e pega o artefato assinado.

  • iOS: a configuração mais simples é a assinatura automática no Xcode (Signing & Capabilities). Para equipes e CI, use o fastlane match.
  • Android: crie um keystore de upload, configure signingConfigs no Gradle e ative o Play App Signing no primeiro upload. Mantenha o keystore fora do git, por exemplo no release/keys/, que está no gitignore.

Assinatura iOS sem acesso de proprietário

No iOS, assinar o app e enviá-lo exigem coisas diferentes, e ambas costumam estar com o Account Holder ou um Admin. O appship continua sem fazer o build nem assinar por você. Ele audita os arquivos que você recebeu, instala-os e repassa a configuração de assinatura ao seu comando de build.

Sua situaçãoAssinar comEnviar com
Account Holder ou AdminAssinatura automática ou fastlane matchChave de API da equipe
O proprietário enviou os arquivos de assinatura e uma chave de API da equipeArquivos de ios.signingChave de API da equipe
O proprietário enviou os arquivos de assinatura, sem chave de APIArquivos de ios.signingSua própria chave de API individual
Nenhuma chave de APIArquivos de ios.signingTransporter ou Xcode Organizer, manualmente
O proprietário enviou apenas uma chave de APIPeça um certificado e um perfil, ou use a assinatura automática do Xcode se a sua função permitirChave de API

Peça ao proprietário

  • Um certificado Apple Distribution em .p12, exportado do Keychain Access com uma senha. Ele deve incluir a chave privada.
  • Um provisioning profile App Store (.mobileprovision) para cada bundle id, incluindo extensões do app.
  • Opcionalmente, uma chave de API da equipe: .p8, Key ID e Issuer ID.

Para evitar transportar uma chave privada, crie uma certificate signing request no seu próprio Mac e peça ao proprietário que emita o certificado a partir dela. Assim, a chave privada nunca sai da sua máquina e você não precisa do .p12.

Configurar e instalar

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # instala os perfis, importa o .p12
appship build --ios
appship doctor                                    # audita os perfis, o keychain e o .ipa gerado
appship upload --ios

A senha do .p12 nunca é gravada no release.yml; passe-a em APPSHIP_P12_PASSWORD. O comando de build recebe $APPSHIP_EXPORT_OPTIONS (um ExportOptions.plist gerado), $APPSHIP_IOS_BUNDLE_ID e $APPSHIP_IOS_TEAM_ID. Para o fastlane gym, use --export_options "$APPSHIP_EXPORT_OPTIONS". O plist controla apenas a etapa de exportação; com assinatura manual, desative também a assinatura automática no projeto Xcode para que a etapa de archive use o mesmo perfil.

O que o doctor verifica

  • Cada perfil é um perfil iOS App Store, não está expirado (aviso com menos de 30 dias), é da equipe em ios.team_id e cobre o ios.bundle_id.
  • O .p12 existe e não é legível por todos, e um certificado correspondente com a sua chave privada está no keychain (somente macOS).
  • O .ipa gerado está assinado para o bundle id correto, com um perfil válido de ios.signing.profiles.
  • build_command realmente usa $APPSHIP_EXPORT_OPTIONS.

Sem chave de API da equipe

  • Chave individual: no App Store Connect, Integrations → Individual Keys. Ela não tem Issuer ID, então deixe issuer_id vazio: appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. Ela carrega as permissões da sua própria função, e um Admin pode desativar o recurso. Ainda não verificado em uma conta real.
  • Nenhuma chave: assine e faça o build da mesma forma e depois envie o .ipa com o Transporter ou pelo Xcode → Organizer → Distribute App. doctor ainda audita o arquivo antes. O appship não envia com um Apple ID, pois isso exige 2FA interativo.

No CI

passos do GitHub Actions
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

Isso cria um keychain dedicado, então o keychain de login do runner não é alterado. Perfis e certificados expiram após cerca de um ano; o doctor avisa 30 dias antes.

As funções diferem no que podem fazer; consulte a tabela de funções na Ajuda do App Store Connect. As telas da Apple mudam, então considere os passos válidos em 09/2026.

De onde as chaves são lidas

Para cada valor, vale a primeira fonte encontrada. Você pode combiná-las, por exemplo um perfil na sua máquina e variáveis de ambiente no CI.

  1. Variáveis de ambiente: APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH ou APPSHIP_ASC_KEY (conteúdo, texto simples ou base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH ou APPSHIP_PLAY_JSON e APPSHIP_PROFILE.
  2. release/release.yml: caminhos para arquivos no release/keys/, que está no gitignore. Key ID e Issuer ID não são segredos e podem ser commitados.
  3. Um perfil: credentials.profile: my-company, apontando para ~/.appship/credentials/my-company/.
release/release.yml, sem um perfil
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # opcional
  android:
    json_key_path: release/keys/play-service-account.json

Se uma chave for commitada

  1. Revogue-a imediatamente. iOS: App Store Connect → Integrations → Revoke. Android: Cloud Console → a conta de serviço → Keys → Delete.
  2. Crie uma nova chave e atualize o seu perfil ou os secrets do CI.
  3. Execute git rm --cached <file>. A chave continua no histórico do git, por isso revogá-la é o passo que importa.
