Fluxo de trabalho

Cinco comandos, de um repositório vazio até a App Review.

Configure uma vez por projeto, verifique tudo e repita os dois últimos a cada lançamento.

  1. Uma vez por projeto appship init

    Detecta seu framework, bundle id e nome do pacote, depois cria release/ com modelos comentados e atualiza o .gitignore.

  2. Antes de cada upload appship doctor

    Verifica ferramentas, chaves, limites de caracteres, tamanhos de imagem e textos provisórios, e falha se houver uma chave commitada no git.

  3. Só na primeira vez appship first-release

    Cria o app iOS, envia a página da loja e a App Privacy, e gera o CHECKLIST.md com as etapas que as lojas mantêm manuais.

  4. A cada lançamento appship upload --build

    Executa seu comando de build e envia o .ipa para o TestFlight e o .aab para uma faixa do Google Play, com lançamento gradual.

  5. A cada lançamento appship submit

    Envia o build iOS para a App Review e promove o lançamento Android para produção, depois da sua confirmação.

O que é automatizado

Sem rodeios sobre o que as lojas deixam uma ferramenta fazer.

Apple e Google mantêm algumas etapas manuais de propósito. O appship automatiza o que as APIs delas permitem. Para todo o resto, ele entrega um checklist com as suas respostas já preenchidas.

  • Automatizado o appship faz
  • Apple ID exige login com 2FA, então não roda no CI
  • Checklist sem API; copie suas respostas para o console

Uma configuração por projeto

O repositório do seu app ganha apenas uma pasta release/. A lógica de lançamento fica na ferramenta, então atualizar o appship atualiza todos os projetos que o usam.

release/release.yml
app:
  name: "Word Bank"
  primary_locale: en-US
ios:
  bundle_id: com.ketch.wordbank
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
android:
  package_name: com.ketch.wordbank
  track: internal
  rollout: 1         # 0.2 = 20% staged rollout
credentials:
  profile: ketch-studio

Perguntas das lojas, respondidas uma vez

Classificação etária, conformidade de exportação, direitos de conteúdo, contato do revisor. Escreva as respostas em questionnaire.yml; o appship preenche o que as APIs permitem e coloca o resto no CHECKLIST.md.

release/questionnaire.yml
ios:
  export_compliance:
    uses_non_exempt_encryption: false
  content_rights:
    uses_third_party_content: false
  age_rating:
    gamblingSimulated: NONE
    violenceCartoonOrFantasy: NONE
    messagingAndChat: false
    ageAssurance: false

doctor pega o problema antes das lojas

Limites de caracteres, URLs inválidas, TODOs esquecidos, tamanhos de imagem errados, artefatos desatualizados, chaves ausentes. Cada problema vem com a correção.

appship doctor

Chaves fora do git

As chaves são buscadas primeiro nas variáveis de ambiente, depois em release/keys/ (ignorada pelo git) e por fim em um perfil em ~/.appship salvo com permissão 600. Senhas são mascaradas no --dry-run.

Funciona com qualquer stack

O appship executa seu comando de build e localiza o .ipa e o .aab. Projetos Flutter, React Native, Cocos Creator e nativos são detectados no init.

Pergunta antes de gravar

Enviar para revisão, publicar em produção e sobrescrever uma página publicada pedem confirmação. No CI, passe --yes explicitamente.

Pronto para CI

Passe a chave .p8 em texto simples ou base64 em APPSHIP_ASC_KEY. Um workflow do GitHub Actions pronto está no guia de integração.

Pronto para publicar?

O appship é distribuído no npm. Você precisa do Node.js 22+, do fastlane e de macOS para builds iOS (o Android também funciona no Linux).

$ npm i -g appship-ai
