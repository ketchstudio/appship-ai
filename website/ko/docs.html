초기 릴리스입니다. v0.1.0은 테스트와 dry-run으로 검증되었지만 실제 스토어에서는 아직 실행해 본 적이 없습니다. 스토어에 쓰는 모든 명령은 --dry-run을 지원하니, appship status 같은 읽기 전용 명령부터 시작하세요.

1요구 사항

필요한 것비고
Node.js 22 이상appship은 npm 패키지입니다.
fastlaneappship은 모든 스토어 호출에 fastlane을 사용합니다. 사용 중인 컴퓨터에 맞게 fastlane 문서에서 권장하는 방식으로 설치하세요.
Xcode가 설치된 macOSiOS 빌드와 업로드에만 필요합니다. Android 전용 프로젝트는 Linux에서도 동작합니다.
Apple Developer Program연 99 USD.
Google Play Console 계정25 USD, 1회 결제.
서명된 릴리스를 빌드하는 앱appship은 서명을 대신해 주지 않습니다. 서명을 참고하세요.

2설치

appship은 컴퓨터마다 한 번, 전역으로 설치합니다. 앱의 package.json에는 아무것도 추가되지 않습니다.

terminal
npm i -g appship-ai
appship --version

패키지 이름은 appship-ai이며 appship 명령을 설치합니다. 설치하지 않고 써 보려면 npx appship-ai --help를 실행하세요.

3스토어 키 발급

프로젝트마다가 아니라 개발자 계정마다 한 번만 하면 됩니다. 두 키 모두 내 이름으로 빌드를 게시할 수 있으므로 절대 git에 커밋하지 마세요.

iOS: App Store Connect API 키

  1. App Store Connect에서 Users and Access → Integrations → App Store Connect API를 엽니다.
  2. Team Keys 아래에서 +를 클릭합니다. 이름은 appship으로 하고 App Manager 역할을 부여합니다.
  3. AuthKey_XXXXXXXXXX.p8을 다운로드합니다. Apple은 한 번만 다운로드할 수 있게 합니다.
  4. Key ID(10자, 파일 이름에도 들어 있음)와 Issuer ID(키 표 위에 있는 UUID)를 메모해 둡니다.

Team Keys는 Account Holder 또는 Admin만 만들 수 있습니다. 본인이 아니라면 소유자에게 키를 보내 달라고 요청하거나, 개인 키를 쓰는 방법은 소유자 권한 없이 iOS 서명하기를 참고하세요.

Apple ID(이메일)는 선택 사항입니다. 앱 레코드를 만들고 App Privacy 답변을 업로드할 때만 필요한데, Apple의 API 키로는 이 두 가지를 할 수 없기 때문입니다. 2단계 인증이 필요하므로 CI에서는 사용할 수 없습니다.

Android: Google Play 서비스 계정

  1. Google Cloud Console에서 프로젝트를 선택하고 Google Play Android Developer API를 사용 설정합니다.
  2. IAM & Admin → Service Accounts → Create service account로 이동합니다. GCP 역할은 필요하지 않습니다.
  3. 계정을 열고 Keys → Add key → JSON을 선택해 키 파일을 다운로드합니다.
  4. Play Console에서 Users and permissions → Invite new users로 이동해 JSON 안의 client_email을 초대합니다. Release apps to testing tracks, Release to production, Manage store presence 권한을 부여합니다.
  5. 권한이 적용될 때까지 몇 분간 기다립니다. 새 계정은 최대 24시간이 걸릴 수 있습니다.

프로필로 저장하기

프로필은 키를 모드 600으로 ~/.appship/credentials/<name>/에 복사하므로, 이 컴퓨터의 모든 프로젝트가 키를 공유할 수 있습니다. 플래그 없이 실행하면 단계별로 물어봅니다.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4프로젝트 설정

앱 저장소의 루트에서 init을 실행합니다.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init은 Flutter, React Native, Cocos Creator, 네이티브 프로젝트를 감지하고, 번들 ID와 패키지 이름을 읽어 빌드 명령과 아티팩트 경로를 채웁니다. 아래 폴더를 만들고 release/keys/*와 release/.appship/를 .gitignore에 추가합니다.

project layout
my-app/
└── release/
    ├── release.yml            # ids, artifacts, build commands, tracks, credentials
    ├── questionnaire.yml      # answers to store questions
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # gitignored; only if you don't use a profile
    └── .appship/              # gitignored; scratch files for fastlane

release/release.yml을 열어 각 플랫폼의 artifact와 build_command를 확인하세요. Flutter 앱이라면 다음과 같습니다.

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # release as soon as Apple approves
    phased_release: false      # 7-day phased rollout
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # draft while the app is unpublished
  rollout: 1                   # 0.2 = 20% staged rollout
credentials:
  profile: my-company

keys/와 .appship/를 제외한 release/ 폴더 전체를 커밋하세요. 저장소에는 Fastfile이 생기지 않습니다. 릴리스 로직은 appship 안에 있으므로, appship을 업데이트하면 모든 프로젝트가 함께 업데이트됩니다.

5스토어 등록 정보 작성

앱이 이미 출시된 상태라면 직접 입력하는 대신 현재 등록 정보를 가져오세요.

terminal
appship metadata pull

그렇지 않다면 다음 파일에서 모든 TODO를 바꾸세요.

  • release/questionnaire.yml: 연령 등급, 수출 규정 준수, 콘텐츠 권한, 심사 담당자 연락처, App Privacy, Android 앱 콘텐츠 답변.
  • 텍스트: release/ios/metadata/<locale>/*.txt와 release/android/metadata/<locale>/*.txt.
  • 언어별 릴리스 노트: 로캘마다 폴더 하나. 아래 언어와 릴리스 노트를 참고하세요.
  • iOS 스크린샷은 release/ios/screenshots/<locale>/에: iPhone 6.9" 세트(1320×2868) 또는 6.5" 세트(1284×2778) 중 하나 이상.
  • Android 이미지는 release/android/metadata/<locale>/images/에: icon.png 512×512, featureGraphic.png 1024×500, 그리고 phoneScreenshots/에 이미지 2장 이상.

언어와 릴리스 노트

두 스토어 모두 언어마다 별도의 "What's New" 텍스트를 받습니다. 언어 하나가 폴더 하나이고, 각 폴더에 해당 언어의 릴리스 노트가 들어 있습니다.

스토어파일 (로캘 폴더마다 하나)최대
App Storerelease/ios/metadata/<locale>/release_notes.txt4000자
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500자

언어를 추가하려면 다음과 같이 합니다.

  1. release.yml에 언어를 나열합니다. 이 목록은 선택 사항이며, 없으면 appship이 찾은 모든 폴더를 사용합니다. iOS와 Android는 로캘 코드가 다르므로 플랫폼마다 목록이 따로 있습니다.
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # Play 코드는 다릅니다. 예: 여기서는 zh-CN, iOS에서는 zh-Hans
  2. release/ios/metadata/vi/ 같은 폴더를 만들고 필수 파일을 채웁니다. iOS는 name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt, release_notes.txt이고, Android는 title.txt, short_description.txt, full_description.txt, changelogs/default.txt입니다.
  3. iOS 스크린샷을 release/ios/screenshots/<locale>/에 추가합니다. Android는 먼저 Play Console에서 해당 언어를 활성화하세요.
  4. appship doctor를 실행합니다. 목록에 있는데 폴더가 없는 로캘은 오류입니다. 폴더는 있는데 목록에 없는 경우는 스토어에 그대로 푸시되므로 경고입니다.

알아 두세요.

  • App Store Connect에서 먼저 언어를 추가할 필요는 없습니다. 메타데이터를 푸시할 때 자동으로 생성됩니다.
  • 앱의 첫 버전에서는 release_notes.txt를 비워 두세요. Apple은 버전 1.0에서 릴리스 노트를 받지 않습니다.
  • 릴리스 노트가 없는 로캘은 해당 언어의 "What's New"가 비어 보입니다. 일부 로캘에만 노트가 있으면 doctor가 경고합니다.
  • iOS 폴더 이름은 en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans, zh-Hant처럼 Apple의 코드 중 하나여야 합니다. doctor는 zh-CN 같은 다른 이름을 거부합니다.
  • fastlane의 공용 default 폴더는 아직 지원하지 않습니다.

추천 언어

다음에 어떤 언어를 추가할지 고민되시나요? appship은 사용자층이 큰 여섯 가지 언어를 추천합니다. 스페인어(스페인과 중남미), 브라질 포르투갈어, 독일어, 프랑스어, 일본어, 한국어입니다. 두 스토어는 서로 다른 코드를 사용합니다.

언어--locales idiOS 폴더Android 폴더
스페인어(스페인)eses-ESes-ES
스페인어(중남미)eses-MXes-419
포르투갈어(브라질)pt-BRpt-BRpt-BR
독일어dede-DEde-DE
프랑스어frfr-FRfr-FR
일본어jajaja-JP
한국어kokoko-KR
  • 프로젝트를 설정할 때 폴더를 만드세요. 여섯 가지 모두 만들려면 appship init --locales preset, 일부만 만들려면 --locales es,ja를 사용합니다. 각 플랫폼의 locales를 올바른 코드로 작성하고, 번역할 수 있도록 TODO로 채운 등록 정보 파일을 만들어 줍니다. doctor는 모든 TODO를 바꿀 때까지 실패합니다.
  • 이미 존재하는 프로젝트는 위의 코드로 폴더를 직접 추가하세요(init --force는 release.yml을 덮어씁니다).
  • 스페인어는 실제로 작성할 변형만 남기세요. iOS의 es-MX와 Play의 es-419는 중남미 전체를 포괄합니다.
  • 스토어 제한은 바이트나 단어가 아니라 글자 수로 계산합니다. 일본어와 한국어 텍스트는 보통 영어보다 짧고, 독일어와 프랑스어는 더 길어서 30자 제목 제한에 자주 걸립니다.
  • 업로드하기 전에 Play Console에서 각 언어를 활성화하세요. doctor는 Play 언어 코드가 아닌 Android 폴더에 대해 경고하고 해결 방법을 제안합니다. 예를 들어 ja는 ja-JP여야 합니다.
  • release-notes 스킬은 각 언어의 관례를 알고 있습니다. 존댓말과 반말, 지역별 변형, 일본어 전각 문장부호, ? ! : ; 앞의 프랑스어 띄어쓰기 등입니다.

Claude Code로 릴리스 노트 작성하기

appship init은 Claude Code 스킬인 release-notes를 프로젝트의 .claude/skills/에 설치합니다. 릴리스하기 전에 Claude에게 "이번 버전의 릴리스 노트를 작성해 줘"라고 요청하거나 /release-notes를 실행하세요. 그러면 다음을 수행합니다.

  1. release.yml과 로캘 폴더를 읽습니다.
  2. 마지막 태그 이후의 git log와, 있다면 CHANGELOG.md를 읽습니다.
  3. 기본 언어로 사용자 관점의 짧은 노트를 작성하고 나머지 모든 로캘로 번역합니다.
  4. 스토어 제한에 맞추고, 파일을 쓴 뒤 appship doctor를 실행합니다.

노트는 일반 파일로 남으므로 검토하고 수정할 수 있습니다. 스킬은 이미 있는 텍스트를 덮어쓰기 전에 먼저 묻고, 스토어에는 아무것도 푸시하지 않습니다. 이 기능이 추가되기 전에 설정한 프로젝트라면 스킬을 직접 복사해 넣으세요.

terminal
mkdir -p .claude/skills
cp -r "$(npm root -g)/appship-ai/skills/release-notes" .claude/skills/

6doctor로 점검

doctor는 도구, 설정, 키, 아티팩트, 글자 수 제한, 이미지 크기, 자리 표시 텍스트를 점검하고, 키 파일이 git에 추적되고 있으면 실패합니다. ✗가 없어질 때까지 반복하세요. !는 경고이며 릴리스를 막지 않습니다.

appship doctor
▸ Security
  ✓ No key files tracked by git
  ✓ .gitignore protects release/keys/
▸ iOS · store listing
  ✗ ios/metadata/en-US/subtitle.txt is 34 characters (max 30)
▸ Android · store listing
  ✓ Metadata OK for en-US

  ✗ 1 error(s), 0 warning(s)

7첫 릴리스

terminal
appship build
appship first-release --create-app
  • iOS: App Store Connect에 앱을 만들고(Apple ID가 필요하며 2단계 인증 코드를 물어볼 수 있습니다), 이어서 등록 정보, 스크린샷, 연령 등급, 심사 정보, App Privacy를 푸시합니다.
  • Android: Google Play에는 앱을 만드는 API가 없으므로 appship은 대신 진행 단계를 출력합니다.
  • 두 플랫폼 모두 release/CHECKLIST.md를 작성합니다. 콘솔에서 직접 해야 하는 단계와, 복사해서 쓸 수 있도록 questionnaire.yml의 답변이 들어 있습니다.

Google Play에서는 체크리스트에 따라 다음을 진행합니다.

  1. Play Console에서 앱을 만듭니다.
  2. 앱에 서비스 계정을 초대합니다.
  3. 첫 .aab를 Internal testing에 직접 업로드합니다.
  4. 앱 콘텐츠 섹션을 작성합니다.

Android 앱이 한 번도 게시된 적이 없는 동안에는 release.yml에서 release_status: draft로 설정하세요. 신규 개인 개발자 계정은 프로덕션 배포 전에 테스터 12명과 함께 14일간 비공개 테스트도 진행해야 합니다.

이어서 첫 릴리스를 마무리합니다.

terminal
appship metadata --android
appship upload
appship submit

8이후 매 릴리스

프로젝트의 버전과 빌드 번호를 올린 다음 아래를 실행합니다.

terminal
# Claude Code에 릴리스 노트 작성을 요청합니다 (언어와 릴리스 노트 참고)
appship upload --build   # 빌드 후 TestFlight + Google Play 트랙에 업로드 (기본은 internal)
# TestFlight / internal 트랙에서 테스트합니다
appship submit           # iOS: 앱 심사 제출 · Android: 프로덕션으로 승격
appship status           # 두 스토어의 심사 상태와 버전

Android에서 단계적 출시를 하려면 다음과 같이 합니다.

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

스토어에 쓰는 모든 명령은 실행 전에 먼저 확인을 요청합니다. --dry-run을 추가하면 실제로 전송될 내용을 정확히 확인할 수 있습니다.

9CI에서 실행

CI에서는 키를 시크릿에서 APPSHIP_* 환경 변수로 가져오며, 쓰기 명령에는 모두 --yes가 필요합니다. 다음 저장소 시크릿을 추가하세요(GitHub에서는 Settings → Secrets and variables → Actions).

시크릿값
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYbase64 -i AuthKey_XXX.p8의 출력
APPSHIP_PLAY_JSONbase64 -i play-service-account.json의 출력
서명 시크릿서명 방식에 따라 다릅니다. 예: fastlane match용 MATCH_PASSWORD, 또는 base64로 인코딩한 Android 키스토어

GitHub Actions 워크플로의 릴리스 단계는 다음과 같습니다.

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # iOS 빌드에는 macOS가 필요합니다
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...툴체인, fastlane, 서명 설정...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Flutter 설정과 서명 단계를 직접 추가하고, submit을 수동으로 실행하고 싶다면 위와 같은 workflow_dispatch 입력을 추가하세요.

  • iOS 앱 생성과 App Privacy 업로드에는 2단계 인증이 걸린 Apple ID가 필요합니다. CI가 아니라 내 컴퓨터에서 한 번만 진행하세요.
  • fastlane 버전을 고정하려면 Gemfile을 사용하고 APPSHIP_FASTLANE="bundle exec fastlane"을 설정하세요.
  • 파이프라인이 무언가를 푸시하기 전에 --dry-run으로 처음부터 끝까지 먼저 시험해 보세요.

참고

서명

appship은 앱을 빌드하거나 서명하지 않습니다. build_command를 실행하고 서명된 아티팩트를 가져올 뿐입니다.

  • iOS: 가장 간단한 방법은 Xcode의 자동 서명(Signing & Capabilities)입니다. 팀과 CI에서는 fastlane match를 사용하세요.
  • Android: 업로드 키스토어를 만들고, Gradle에서 signingConfigs를 설정하고, 첫 업로드 때 Play App Signing을 켭니다. 키스토어는 git에 넣지 말고, 예를 들어 gitignore 처리된 release/keys/에 두세요.

소유자 권한 없이 iOS 서명하기

iOS에서는 앱 서명과 업로드에 필요한 것이 서로 다르며, 둘 다 보통 Account Holder나 Admin이 가지고 있습니다. 이 경우에도 appship이 대신 빌드하거나 서명하지는 않습니다. 전달받은 파일을 점검하고, 설치하고, 서명 설정을 빌드 명령에 넘겨줍니다.

내 상황서명 방법업로드 방법
Account Holder 또는 Admin자동 서명 또는 fastlane match팀 API 키
소유자가 서명 파일과 팀 API 키를 보내 준 경우ios.signing 파일팀 API 키
소유자가 서명 파일은 보냈지만 API 키는 없는 경우ios.signing 파일내 개인 API 키
API 키가 전혀 없는 경우ios.signing 파일Transporter 또는 Xcode Organizer로 직접 업로드
소유자가 API 키만 보낸 경우인증서와 프로필을 요청하거나, 역할이 허용한다면 Xcode 자동 서명API 키

소유자에게 요청할 것

  • Apple Distribution 인증서를 .p12 형식으로, Keychain Access에서 비밀번호를 걸어 내보낸 것. 개인 키가 포함되어 있어야 합니다.
  • 앱 익스텐션을 포함해 각 번들 ID에 대한 App Store 프로비저닝 프로필(.mobileprovision).
  • 선택 사항으로 팀 API 키: .p8, Key ID, Issuer ID.

개인 키를 주고받지 않으려면, 내 Mac에서 인증서 서명 요청(CSR)을 만들고 소유자가 그 요청으로 인증서를 발급하게 하세요. 그러면 개인 키가 내 컴퓨터를 벗어나지 않으므로 .p12가 필요 없습니다.

설정 및 설치

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # 프로필을 설치하고 .p12를 가져옵니다
appship build --ios
appship doctor                                    # 프로필, 키체인, 빌드된 .ipa를 점검합니다
appship upload --ios

.p12 비밀번호는 release.yml에 저장하지 않으며 APPSHIP_P12_PASSWORD로 전달합니다. 빌드 명령은 $APPSHIP_EXPORT_OPTIONS(생성된 ExportOptions.plist), $APPSHIP_IOS_BUNDLE_ID, $APPSHIP_IOS_TEAM_ID를 받습니다. fastlane gym에서는 --export_options "$APPSHIP_EXPORT_OPTIONS"를 사용하세요. plist는 내보내기 단계만 제어하므로, 수동 서명을 쓸 때는 아카이브 단계도 같은 프로필을 쓰도록 Xcode 프로젝트에서 자동 서명도 꺼야 합니다.

doctor가 점검하는 항목

  • 각 프로필이 iOS App Store 프로필이고, 만료되지 않았으며(30일 미만이면 경고), ios.team_id의 팀에서 발급되었고, ios.bundle_id를 포함하는지 확인합니다.
  • .p12가 존재하고 다른 사용자가 읽을 수 없는지, 그리고 개인 키가 있는 일치하는 인증서가 키체인에 있는지 확인합니다(macOS만 해당).
  • 빌드된 .ipa가 올바른 번들 ID로 서명되었고 ios.signing.profiles의 유효한 프로필을 사용하는지 확인합니다.
  • build_command가 실제로 $APPSHIP_EXPORT_OPTIONS를 사용하는지 확인합니다.

팀 API 키가 없을 때

  • 개인 키: App Store Connect의 Integrations → Individual Keys에서 발급합니다. Issuer ID가 없으므로 issuer_id는 비워 두세요. appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. 개인 키는 내 역할의 권한을 그대로 가지며, Admin이 이 기능을 끌 수 있습니다. 실제 계정에서는 아직 검증되지 않았습니다.
  • 키가 전혀 없을 때: 같은 방식으로 서명하고 빌드한 다음 Transporter 또는 Xcode → Organizer → Distribute App으로 .ipa를 업로드하세요. 그래도 doctor가 먼저 파일을 점검합니다. appship은 대화형 2단계 인증이 필요하므로 Apple ID로는 업로드하지 않습니다.

CI에서

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

전용 키체인을 만들기 때문에 러너의 로그인 키체인은 건드리지 않습니다. 프로필과 인증서는 약 1년 뒤 만료되며, doctor는 30일 전에 경고합니다.

역할마다 할 수 있는 일이 다르니 App Store Connect 도움말의 역할 표를 확인하세요. Apple의 화면은 바뀔 수 있으므로 이 단계는 2026년 9월 기준으로 봐 주세요.

키를 읽어 오는 위치

각 값은 처음 발견된 소스가 우선합니다. 소스를 섞어 쓸 수도 있습니다. 예를 들어 내 컴퓨터에서는 프로필을, CI에서는 환경 변수를 사용할 수 있습니다.

  1. 환경 변수: APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH 또는 APPSHIP_ASC_KEY(내용, 일반 텍스트 또는 base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH 또는 APPSHIP_PLAY_JSON, 그리고 APPSHIP_PROFILE.
  2. release/release.yml: gitignore 처리된 release/keys/에 있는 파일의 경로. Key ID와 Issuer ID는 비밀이 아니므로 커밋해도 됩니다.
  3. 프로필: ~/.appship/credentials/my-company/를 가리키는 credentials.profile: my-company.
release/release.yml, without a profile
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # 선택 사항
  android:
    json_key_path: release/keys/play-service-account.json

키를 커밋했을 때

  1. 즉시 폐기하세요. iOS: App Store Connect → Integrations → Revoke. Android: Cloud Console → 해당 서비스 계정 → Keys → Delete.
  2. 새 키를 만들고 프로필이나 CI 시크릿을 업데이트합니다.
  3. git rm --cached <file>을 실행합니다. 키는 git 기록에 그대로 남으므로, 키를 폐기하는 것이 가장 중요한 단계입니다.
