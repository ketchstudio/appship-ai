Thêm appship vào dự án của bạn

Từ một app chưa từng lên store đến một bản build đang chờ App Review. Lần đầu nên dành khoảng một giờ, phần lớn là thời gian lấy key trong các console của Apple và Google.

Bản phát hành sớm. v0.1.0 đã có test và dry-run, nhưng chưa được chạy thử trên store thật. Mọi lệnh ghi lên store đều hỗ trợ --dry-run; hãy bắt đầu bằng các lệnh chỉ đọc như appship status.

2Cài đặt

Cài appship một lần cho mỗi máy, ở chế độ global. Không có gì được thêm vào package.json của app.

terminal
npm i -g appship-ai
appship --version

Package tên là appship-ai và cài lệnh appship. Muốn dùng thử mà không cài, chạy npx appship-ai --help.

3Lấy key của store

Bạn làm bước này một lần cho mỗi tài khoản developer, không phải mỗi dự án. Cả hai key đều có thể publish build dưới tên bạn, vì vậy đừng bao giờ commit chúng lên git.

iOS: App Store Connect API key

  1. Trong App Store Connect, mở Users and Access → Integrations → App Store Connect API.
  2. Ở mục Team Keys, bấm +. Đặt tên appship và cấp role App Manager.
  3. Tải AuthKey_XXXXXXXXXX.p8. Apple chỉ cho tải file này một lần.
  4. Ghi lại Key ID (10 ký tự, cũng nằm trong tên file) và Issuer ID (chuỗi UUID phía trên bảng key).

Chỉ Account Holder hoặc Admin mới tạo được Team Key. Nếu bạn không phải, hãy nhờ owner gửi key, hoặc xem Ký app iOS khi không phải chủ tài khoản để dùng key cá nhân.

Apple ID (email) là tùy chọn. Chỉ cần để tạo app record và upload câu trả lời App Privacy, vì API key của Apple không làm được hai việc này. Apple ID cần 2FA nên không bao giờ chạy được trong CI.

Android: service account của Google Play

  1. Trong Google Cloud Console, chọn một project và bật Google Play Android Developer API.
  2. Vào IAM & Admin → Service Accounts → Create service account. Không cần gán role GCP nào.
  3. Mở account vừa tạo, rồi vào Keys → Add key → JSON để tải file key.
  4. Trong Play Console, vào Users and permissions → Invite new users và mời client_email lấy từ file JSON. Cấp các quyền Release apps to testing tracks, Release to production và Manage store presence.
  5. Chờ vài phút để quyền có hiệu lực. Với tài khoản mới có thể mất tới 24 giờ.

Lưu thành profile

Profile sao chép các key vào ~/.appship/credentials/<name>/ với mode 600, để mọi dự án trên máy này dùng chung. Chạy không kèm flag để được hỏi từng bước.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4Gắn tool vào dự án

Chạy init từ thư mục gốc của repo app.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init nhận diện dự án Flutter, React Native, Cocos Creator hoặc native, đọc bundle id và package name, rồi điền sẵn build command và đường dẫn artifact. Lệnh này tạo thư mục dưới đây và thêm release/keys/* cùng release/.appship/ vào .gitignore:

project layout
my-app/
└── release/
    ├── release.yml            # id, artifact, build command, track, credentials
    ├── questionnaire.yml      # câu trả lời cho các câu hỏi của store
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # đã gitignore; chỉ dùng nếu bạn không dùng profile
    └── .appship/              # đã gitignore; file tạm cho fastlane

Mở release/release.yml và kiểm tra artifact cùng build_command của từng nền tảng. Với app Flutter, file trông như sau:

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # phát hành ngay khi Apple duyệt
    phased_release: false      # phát hành dần trong 7 ngày
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # dùng draft khi app chưa publish
  rollout: 1                   # 0.2 = staged rollout 20%
credentials:
  profile: my-company

Commit cả thư mục release/ trừ keys/ và .appship/. Repo của bạn không có Fastfile: logic release nằm trong appship, nên cập nhật appship là cập nhật cho mọi dự án.

5Điền nội dung store

Nếu app đã có trên store, hãy kéo nội dung hiện tại về thay vì gõ tay:

terminal
appship metadata pull

Nếu không, thay mọi TODO trong các file sau:

  • release/questionnaire.yml: age rating, export compliance, content rights, thông tin liên hệ cho reviewer, App Privacy và các câu trả lời App content của Android.
  • Văn bản: release/ios/metadata/<locale>/*.txt và release/android/metadata/<locale>/*.txt.
  • Release notes theo từng ngôn ngữ: mỗi locale một thư mục. Xem Ngôn ngữ và release notes bên dưới.
  • Screenshot iOS trong release/ios/screenshots/<locale>/: tối thiểu một bộ iPhone 6.9" (1320×2868) hoặc 6.5" (1284×2778).
  • Ảnh Android trong release/android/metadata/<locale>/images/: icon.png 512×512, featureGraphic.png 1024×500 và tối thiểu 2 ảnh trong phoneScreenshots/.

Ngôn ngữ và release notes

Cả hai store đều nhận một đoạn "What's New" riêng cho mỗi ngôn ngữ. Mỗi ngôn ngữ là một thư mục, và mỗi thư mục chứa release notes của riêng nó:

StoreFile, mỗi thư mục locale một fileTối đa
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 ký tự
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 ký tự

Để thêm một ngôn ngữ:

  1. Khai báo nó trong release.yml. Danh sách này là tùy chọn; nếu không có, appship dùng mọi thư mục tìm thấy. iOS và Android dùng mã locale khác nhau, nên mỗi nền tảng có danh sách riêng:
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # mã của Play khác iOS, ví dụ zh-CN ở đây, zh-Hans trên iOS
  2. Tạo thư mục, ví dụ release/ios/metadata/vi/, rồi điền các file bắt buộc: name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt và release_notes.txt cho iOS; title.txt, short_description.txt, full_description.txt và changelogs/default.txt cho Android.
  3. Thêm screenshot iOS vào release/ios/screenshots/<locale>/. Với Android, hãy bật ngôn ngữ đó trong Play Console trước.
  4. Chạy appship doctor. Locale có trong danh sách nhưng không có thư mục là lỗi. Thư mục không có trong danh sách chỉ là cảnh báo, vì nó vẫn được đẩy lên store.

Cần lưu ý:

  • Bạn không cần thêm ngôn ngữ trong App Store Connect trước. Ngôn ngữ được tạo khi metadata được đẩy lên.
  • Để trống release_notes.txt cho phiên bản đầu tiên của app. Apple không nhận release notes ở phiên bản 1.0.
  • Locale không có release notes sẽ hiện "What's New" trống ở ngôn ngữ đó. doctor cảnh báo khi một số locale có notes còn số khác thì không.
  • Tên thư mục iOS phải là một trong các mã của Apple, như en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans hoặc zh-Hant. doctor từ chối mọi mã khác, ví dụ zh-CN.
  • Thư mục default dùng chung của fastlane chưa được hỗ trợ.

  • Tạo các thư mục ngay khi thiết lập dự án: appship init --locales preset cho cả sáu ngôn ngữ, hoặc --locales es,ja cho một số ngôn ngữ. Lệnh ghi locales cho từng nền tảng với đúng mã và tạo các file listing điền sẵn TODO để bạn dịch. doctor báo lỗi cho đến khi mọi TODO được thay.
  • Với dự án đã có sẵn, hãy thêm thư mục bằng tay theo các mã ở trên (init --force sẽ ghi đè release.yml).
  • Chỉ giữ biến thể tiếng Tây Ban Nha mà bạn thực sự sẽ viết. es-MX trên iOS và es-419 trên Play đều bao phủ toàn bộ Mỹ Latin.
  • Giới hạn của store tính theo ký tự, không phải byte hay từ. Văn bản tiếng Nhật và tiếng Hàn thường ngắn hơn tiếng Anh; tiếng Đức và tiếng Pháp dài hơn và hay chạm giới hạn 30 ký tự của tiêu đề.
  • Bật từng ngôn ngữ trong Play Console trước khi upload. doctor cảnh báo thư mục Android không phải mã ngôn ngữ của Play và gợi ý cách sửa, ví dụ ja phải là ja-JP.
  • Skill release-notes nắm quy ước của từng ngôn ngữ: xưng hô trang trọng hay thân mật, biến thể theo vùng, dấu câu full-width của tiếng Nhật và khoảng trắng trước ? ! : ; trong tiếng Pháp.

Viết release notes bằng Claude Code

appship init cài một skill Claude Code tên release-notes vào .claude/skills/ của dự án. Trước khi release, hãy nhờ Claude "write the release notes for this version" (hoặc chạy /release-notes). Skill sẽ:

  1. Đọc release.yml và các thư mục locale.
  2. Đọc git log từ tag gần nhất, và CHANGELOG.md nếu bạn có.
  3. Viết release notes ngắn, hướng tới người dùng bằng ngôn ngữ chính của bạn, rồi dịch sang mọi locale còn lại.
  4. Điều chỉnh cho vừa giới hạn của store, ghi file, rồi chạy appship doctor.

Release notes vẫn là file thường, nên bạn có thể xem lại và sửa. Skill hỏi trước khi ghi đè nội dung đã có, và không bao giờ đẩy gì lên store. Với dự án được thiết lập trước khi có tính năng này, hãy chép skill vào bằng tay:

terminal
mkdir -p .claude/skills
cp -r "$(npm root -g)/appship-ai/skills/release-notes" .claude/skills/

6Kiểm tra bằng doctor

doctor kiểm tra tool, config, key, artifact, giới hạn ký tự, kích thước ảnh và văn bản placeholder, và báo lỗi nếu có file key đang được git theo dõi. Lặp lại cho đến khi không còn ✗. Dấu ! là cảnh báo và không chặn release.

7Release lần đầu

terminal
appship build
appship first-release --create-app
  • iOS: tạo app trên App Store Connect (cần Apple ID và có thể hỏi mã 2FA), rồi đẩy listing, screenshot, age rating, review info và App Privacy.
  • Android: Google Play không có API để tạo app, nên appship in ra các bước cần làm.
  • Cả hai đều ghi release/CHECKLIST.md: các bước trên console phải làm tay, kèm câu trả lời lấy từ questionnaire.yml để bạn chép sang.

Trên Google Play, làm theo checklist để:

  1. Tạo app trong Play Console.
  2. Mời service account vào app.
  3. Upload bản .aab đầu tiên bằng tay lên Internal testing.
  4. Điền mục App content.

Khi app Android chưa từng được publish, đặt release_status: draft trong release.yml. Tài khoản developer cá nhân mới còn phải chạy closed test với 12 tester trong 14 ngày trước khi lên production.

Sau đó hoàn tất release lần đầu:

terminal
appship metadata --android
appship upload
appship submit

8Những lần release sau

Tăng version và build number trong dự án, rồi:

terminal
# nhờ Claude Code viết release notes (xem Ngôn ngữ và release notes)
appship upload --build   # build, rồi TestFlight + track Google Play (mặc định internal)
# test trên TestFlight / internal track
appship submit           # iOS: App Review · Android: promote lên production
appship status           # trạng thái review và các phiên bản trên cả hai store

Để staged rollout trên Android:

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

Mọi lệnh ghi lên store đều hỏi xác nhận trước. Thêm --dry-run để xem chính xác những gì sẽ được gửi đi.

9Chạy trong CI

Trong CI, key lấy từ secret qua các biến môi trường APPSHIP_*, và mọi lệnh ghi đều cần --yes. Thêm các secret sau vào repository (trên GitHub: Settings → Secrets and variables → Actions):

SecretGiá trị
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYKết quả của base64 -i AuthKey_XXX.p8
APPSHIP_PLAY_JSONKết quả của base64 -i play-service-account.json
Secret dùng để kýTùy cách bạn ký, ví dụ MATCH_PASSWORD cho fastlane match, hoặc keystore Android dạng base64

Các bước release của một workflow GitHub Actions:

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # build iOS cần macOS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...toolchain, fastlane và bước thiết lập ký của bạn...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Hãy thêm phần thiết lập Flutter, bước ký của bạn và, nếu muốn kích hoạt submit bằng tay, một input workflow_dispatch như ở trên.

  • Tạo app iOS và upload App Privacy cần Apple ID với 2FA. Hãy làm các việc này một lần trên máy của bạn, không làm trong CI.
  • Để ghim phiên bản fastlane, dùng Gemfile và đặt APPSHIP_FASTLANE="bundle exec fastlane".
  • Chạy thử toàn bộ pipeline với --dry-run trước khi cho nó đẩy bất cứ thứ gì.

Tham khảo

Ký app

appship không build hay ký app của bạn. Nó chạy build_command của bạn và lấy artifact đã ký.

  • iOS: cách đơn giản nhất là để Xcode tự ký (Automatic signing, trong Signing & Capabilities). Với team và CI, dùng fastlane match.
  • Android: tạo upload keystore, cấu hình signingConfigs trong Gradle, và bật Play App Signing ở lần upload đầu tiên. Giữ keystore ngoài git, ví dụ trong thư mục release/keys/ đã gitignore.

Ký app iOS khi không phải chủ tài khoản

Trên iOS, ký app và upload app cần những thứ khác nhau, và cả hai thường do Account Holder hoặc Admin nắm. appship vẫn không build hay ký thay bạn. Nó kiểm tra các file bạn được đưa, cài chúng, và truyền cách ký cho build command của bạn.

Tình huống của bạnKý bằngUpload bằng
Account Holder hoặc AdminAutomatic signing, hoặc fastlane matchTeam API key
Owner gửi file signing và team API keyFile ios.signingTeam API key
Owner gửi file signing, không có API keyFile ios.signingAPI key cá nhân của bạn
Không có API key nàoFile ios.signingTransporter hoặc Xcode Organizer, làm tay
Owner chỉ gửi API keyXin certificate và profile, hoặc dùng Xcode automatic signing nếu role của bạn cho phépAPI key

Nhờ owner gửi

  • Certificate Apple Distribution dạng .p12, export từ Keychain Access kèm mật khẩu. File phải có private key.
  • Provisioning profile loại App Store (.mobileprovision) cho từng bundle id, kể cả app extension.
  • Tùy chọn: team API key gồm .p8, Key ID và Issuer ID.

Để tránh phải chuyển private key qua lại, hãy tự tạo certificate signing request trên Mac của bạn và nhờ owner cấp certificate từ đó. Khi đó private key không bao giờ rời máy bạn, và bạn không cần .p12.

Khai báo và cài đặt

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # cài profile, import .p12
appship build --ios
appship doctor                                    # kiểm tra profile, keychain và file .ipa đã build
appship upload --ios

Mật khẩu .p12 không bao giờ được lưu trong release.yml; hãy truyền qua APPSHIP_P12_PASSWORD. Build command nhận $APPSHIP_EXPORT_OPTIONS (một file ExportOptions.plist được tạo tự động), $APPSHIP_IOS_BUNDLE_ID và $APPSHIP_IOS_TEAM_ID. Với fastlane gym, dùng --export_options "$APPSHIP_EXPORT_OPTIONS". File plist chỉ điều khiển bước export; với manual signing, hãy tắt automatic signing trong project Xcode để bước archive dùng cùng profile.

Những gì doctor kiểm tra

  • Mỗi profile là profile iOS loại App Store, chưa hết hạn (cảnh báo khi còn dưới 30 ngày), thuộc team trong ios.team_id và áp dụng cho ios.bundle_id.
  • File .p12 tồn tại và không cho mọi người đọc, và keychain có certificate khớp kèm private key (chỉ trên macOS).
  • File .ipa đã build được ký đúng bundle id, bằng profile hợp lệ trong ios.signing.profiles.
  • build_command thực sự dùng $APPSHIP_EXPORT_OPTIONS.

Không có team API key

  • Key cá nhân: trong App Store Connect, Integrations → Individual Keys. Loại key này không có Issuer ID, nên để trống issuer_id: appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. Key mang quyền của role của chính bạn, và Admin có thể tắt tính năng này. Chưa được kiểm chứng trên tài khoản thật.
  • Không có key nào: ký và build theo cách tương tự, rồi upload file .ipa bằng Transporter hoặc Xcode → Organizer → Distribute App. doctor vẫn kiểm tra file trước. appship không upload bằng Apple ID, vì cách đó cần 2FA tương tác.

Trong CI

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

Lệnh này tạo một keychain riêng, nên login keychain của runner không bị đụng tới. Profile và certificate hết hạn sau khoảng một năm; doctor cảnh báo trước 30 ngày.

Mỗi role được phép làm những việc khác nhau; hãy xem bảng role trong App Store Connect Help. Giao diện của Apple thay đổi, nên hãy coi các bước này đúng tại thời điểm 09/2026.

Nơi đọc key

Với mỗi giá trị, nguồn đầu tiên tìm thấy sẽ được dùng. Bạn có thể kết hợp các nguồn, ví dụ dùng profile trên máy và biến môi trường trong CI.

  1. Biến môi trường: APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH hoặc APPSHIP_ASC_KEY (nội dung, dạng thường hoặc base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH hoặc APPSHIP_PLAY_JSON, và APPSHIP_PROFILE.
  2. release/release.yml: đường dẫn tới các file trong release/keys/ đã gitignore. Key ID và Issuer ID không phải bí mật và có thể commit.
  3. Một profile: credentials.profile: my-company, trỏ tới ~/.appship/credentials/my-company/.
release/release.yml, không dùng profile
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # tùy chọn
  android:
    json_key_path: release/keys/play-service-account.json

Nếu lỡ commit key

  1. Thu hồi key ngay. iOS: App Store Connect → Integrations → Revoke. Android: Cloud Console → service account → Keys → Delete.
  2. Tạo key mới và cập nhật profile hoặc secret trong CI.
  3. Chạy git rm --cached <file>. Key vẫn còn trong lịch sử git, vì vậy thu hồi key mới là bước quan trọng.
