Guía de integración · v0.1.0

Añade appship a tu proyecto

Desde una app que nunca ha estado en las tiendas hasta un build en App Review. Calcula aproximadamente una hora la primera vez, la mayor parte para conseguir las claves en las consolas de Apple y Google.

Versión temprana. La v0.1.0 está cubierta por tests y dry-runs, pero aún no se ha probado contra las tiendas reales. Todos los comandos que escriben en una tienda admiten --dry-run; empieza con comandos de solo lectura como appship status.

2Instalación

Instala appship una vez por máquina, de forma global. No se añade nada al package.json de tu app.

terminal
npm i -g appship-ai
appship --version

El paquete se llama appship-ai e instala el comando appship. Para probarlo sin instalar, ejecuta npx appship-ai --help.

3Consigue las claves de las tiendas

Esto se hace una vez por cuenta de desarrollador, no por proyecto. Ambas claves pueden publicar builds a tu nombre, así que nunca las subas a git.

iOS: clave de la API de App Store Connect

  1. En App Store Connect, abre Users and Access → Integrations → App Store Connect API.
  2. En Team Keys, haz clic en +. Ponle el nombre appship y asígnale el rol App Manager.
  3. Descarga AuthKey_XXXXXXXXXX.p8. Apple solo te deja descargarla una vez.
  4. Anota el Key ID (10 caracteres, también en el nombre del archivo) y el Issuer ID (el UUID que aparece sobre la tabla de claves).

Las Team Keys solo puede crearlas un Account Holder o un Admin. Si no eres tú, pide al propietario que te envíe la clave, o consulta Firma de iOS sin acceso de propietario para usar una clave individual.

El Apple ID (correo) es opcional. Solo hace falta para crear el registro de la app y subir las respuestas de App Privacy, porque la clave de la API de Apple no puede hacer ninguna de las dos cosas. Requiere 2FA, así que nunca funciona en CI.

Android: cuenta de servicio de Google Play

  1. En Google Cloud Console, elige un proyecto y activa la Google Play Android Developer API.
  2. Ve a IAM & Admin → Service Accounts → Create service account. No necesita ningún rol de GCP.
  3. Abre la cuenta y ve a Keys → Add key → JSON para descargar el archivo de clave.
  4. En Play Console, ve a Users and permissions → Invite new users e invita al client_email del JSON. Concede Release apps to testing tracks, Release to production y Manage store presence.
  5. Espera unos minutos a que se apliquen los permisos. En una cuenta nueva puede tardar hasta 24 horas.

Guárdalas como perfil

Un perfil copia las claves a ~/.appship/credentials/<name>/ con permisos 600, de modo que todos los proyectos de esta máquina puedan compartirlas. Ejecútalo sin flags para que te pregunte paso a paso.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4Configura el proyecto

Ejecuta init desde la raíz del repositorio de tu app.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init detecta proyectos Flutter, React Native, Cocos Creator o nativos, lee tu bundle id y tu package name, y rellena el comando de build y la ruta del artefacto. Crea esta carpeta y añade release/keys/* y release/.appship/ a .gitignore:

project layout
my-app/
└── release/
    ├── release.yml            # ids, artefactos, comandos de build, tracks, credenciales
    ├── questionnaire.yml      # respuestas a las preguntas de las tiendas
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # en gitignore; solo si no usas un perfil
    └── .appship/              # en gitignore; archivos temporales para fastlane

Abre release/release.yml y revisa artifact y build_command de cada plataforma. Para una app Flutter se ve así:

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # publicar en cuanto Apple apruebe
    phased_release: false      # despliegue gradual en 7 días
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # draft mientras la app no esté publicada
  rollout: 1                   # 0.2 = despliegue gradual al 20 %
credentials:
  profile: my-company

Haz commit de toda la carpeta release/ excepto keys/ y .appship/. Tu repositorio no recibe ningún Fastfile: la lógica de publicación se queda en appship, así que al actualizar appship se actualizan todos los proyectos.

5Completa la ficha

Si la app ya está publicada, descarga la ficha actual en lugar de escribirla:

terminal
appship metadata pull

Si no, sustituye cada TODO en estos archivos:

  • release/questionnaire.yml: clasificación por edades, cumplimiento de exportación, derechos de contenido, contacto para el revisor, App Privacy y las respuestas de App content de Android.
  • Texto: release/ios/metadata/<locale>/*.txt y release/android/metadata/<locale>/*.txt.
  • Notas de versión por idioma: una carpeta por locale. Consulta Idiomas y notas de versión más abajo.
  • Capturas de pantalla de iOS en release/ios/screenshots/<locale>/: al menos un set de iPhone de 6,9" (1320×2868) o de 6,5" (1284×2778).
  • Imágenes de Android en release/android/metadata/<locale>/images/: icon.png de 512×512, featureGraphic.png de 1024×500 y al menos 2 imágenes en phoneScreenshots/.

Idiomas y notas de versión

Ambas tiendas piden un texto "What's New" distinto para cada idioma. Cada idioma es una carpeta, y cada carpeta contiene sus propias notas de versión:

TiendaArchivo, uno por carpeta de localeMáx.
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 caracteres
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 caracteres

Para añadir un idioma:

  1. Inclúyelo en release.yml. La lista es opcional; sin ella, appship usa todas las carpetas que encuentre. iOS y Android usan códigos de locale distintos, así que cada plataforma tiene su propia lista:
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # los códigos de Play difieren, p. ej. zh-CN aquí, zh-Hans en iOS
  2. Crea la carpeta, por ejemplo release/ios/metadata/vi/, y rellena los archivos obligatorios: name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt y release_notes.txt en iOS; title.txt, short_description.txt, full_description.txt y changelogs/default.txt en Android.
  3. Añade las capturas de iOS en release/ios/screenshots/<locale>/. En Android, activa antes el idioma en Play Console.
  4. Ejecuta appship doctor. Un locale de la lista sin carpeta es un error. Una carpeta que no está en la lista es una advertencia, porque igualmente se envía a la tienda.

Conviene saber:

  • No hace falta añadir antes el idioma en App Store Connect. Se crea al enviar los metadatos.
  • Deja release_notes.txt vacío en la primera versión de una app. Apple no acepta notas de versión en la 1.0.
  • Un locale sin notas de versión muestra un "What's New" vacío en ese idioma. doctor avisa cuando algunos locales tienen notas y otros no.
  • Los nombres de carpeta de iOS deben ser uno de los códigos de Apple, como en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans o zh-Hant. doctor rechaza cualquier otro, por ejemplo zh-CN.
  • La carpeta compartida default de fastlane aún no está soportada.

Idiomas sugeridos

¿No sabes qué idiomas añadir después? appship sugiere seis con mucha audiencia: español (España y Latinoamérica), portugués de Brasil, alemán, francés, japonés y coreano. Las dos tiendas usan códigos distintos:

Idiomaid de --localesCarpeta de iOSCarpeta de Android
Español, Españaeses-ESes-ES
Español, Latinoaméricaeses-MXes-419
Portugués, Brasilpt-BRpt-BRpt-BR
Alemándede-DEde-DE
Francésfrfr-FRfr-FR
Japonésjajaja-JP
Coreanokokoko-KR
  • Crea las carpetas al configurar un proyecto: appship init --locales preset para los seis, o --locales es,ja para algunos. Escribe locales de cada plataforma con los códigos correctos y crea archivos de ficha rellenos con TODO para que los traduzcas. doctor falla hasta que se sustituyan todos los TODO.
  • En un proyecto que ya existe, añade las carpetas a mano con los códigos de arriba (init --force reescribiría release.yml).
  • Conserva solo la variante de español que de verdad vayas a escribir. es-MX en iOS y es-419 en Play cubren toda Latinoamérica.
  • Los límites de las tiendas cuentan caracteres, no bytes ni palabras. El texto en japonés y coreano suele ser más corto que en inglés; el alemán y el francés son más largos y con frecuencia chocan con el límite de 30 caracteres del título.
  • Activa cada idioma en Play Console antes de subir. doctor avisa si una carpeta de Android no es un código de idioma de Play y sugiere la corrección, por ejemplo ja debería ser ja-JP.
  • El skill release-notes conoce las convenciones de cada idioma: trato formal o informal, variantes regionales, la puntuación de ancho completo del japonés y el espaciado del francés antes de ? ! : ;.

Escribe las notas de versión con un agente de programación con IA

appship init instala un skill, release-notes, para tu agente de programación con IA (Claude Code, Codex o Antigravity): en .claude/skills/ para Claude Code y en .agents/skills/ para Codex y Antigravity. Antes de publicar, pídele al agente que "escriba las notas de versión de esta versión" (o ejecuta /release-notes en Claude Code o $release-notes en Codex). Hará lo siguiente:

  1. Leerá release.yml y las carpetas de locale.
  2. Leerá git log desde la última etiqueta, y CHANGELOG.md si tienes uno.
  3. Escribirá notas breves, pensadas para el usuario, en tu idioma principal y las traducirá a todos los demás locales.
  4. Ajustará los límites de las tiendas, escribirá los archivos y luego ejecutará appship doctor.

Las notas siguen siendo archivos normales, así que puedes revisarlas y editarlas. El skill pregunta antes de sobrescribir texto que ya exista y nunca envía nada a una tienda.

Capturas de pantalla y declaraciones de las tiendas con un agente de IA

init instala otros dos skills junto a él. Igual que release-notes, solo escriben archivos en release/, ejecutan appship doctor y te dejan a ti el envío a las tiendas.

  • store-screenshots: planifica las capturas contigo, las toma desde el simulador de iOS o un emulador de Android, añade un titular traducido para cada idioma y genera cada imagen en un tamaño que acepta cada tienda (iPhone 6.9" 1320×2868, iPad 13" si la app funciona en iPad, Play 1080×1920), además del icono y el gráfico destacado de Play.
  • app-content: rellena release/questionnaire.yml (clasificación por edades, App Privacy, cumplimiento de exportación, Data safety, clasificación de contenido, público objetivo, anuncios, acceso a la app) a partir de tus dependencias, permisos y código, te pregunta lo que el código no puede mostrar y mantiene las respuestas coherentes entre las dos tiendas.
AgenteCarpeta de skillsCómo ejecutarlo
Claude Code.claude/skills//store-screenshots
Codex.agents/skills/$store-screenshots o /skills
Antigravity.agents/skills/pídele "use the store-screenshots skill"

appship nunca llama a una IA por sí mismo. Abre el agente en la raíz del proyecto, con la sesión iniciada en tu propia cuenta, y aprueba los comandos que te pida ejecutar.

Elige los agentes al ejecutar init, o instala y actualiza los skills más tarde, por ejemplo después de actualizar appship:

terminal
appship init --agents all             # skills para Claude Code, Codex y Antigravity
appship skills                        # qué skills tiene cada agente
appship skills add --agent codex      # instala para Codex / Antigravity (.agents/skills/)
appship skills add --force            # los reemplaza por los de esta versión

6Comprueba con doctor

doctor revisa herramientas, configuración, claves, artefactos, límites de caracteres, tamaños de imagen y texto de relleno, y falla si git rastrea algún archivo de clave. Repítelo hasta que no quede ningún ✗. Un ! es una advertencia y no bloquea la publicación.

appship doctor
▸ Security
  ✓ No key files tracked by git
  ✓ .gitignore protects release/keys/
▸ iOS · store listing
  ✗ ios/metadata/en-US/subtitle.txt is 34 characters (max 30)
▸ Android · store listing
  ✓ Metadata OK for en-US

  ✗ 1 error(s), 0 warning(s)

7Primera publicación

terminal
appship build
appship first-release --create-app
  • iOS: crea la app en App Store Connect (necesita el Apple ID y puede pedirte un código 2FA), y luego envía la ficha, las capturas, la clasificación por edades, la información para la revisión y App Privacy.
  • Android: Google Play no tiene una API para crear apps, así que appship muestra los pasos en su lugar.
  • Ambos escriben release/CHECKLIST.md: los pasos de las consolas que hay que hacer a mano, con tus respuestas de questionnaire.yml listas para copiar.

En Google Play, sigue la lista de comprobación para:

  1. Crear la app en Play Console.
  2. Invitar a la cuenta de servicio a la app.
  3. Subir a mano el primer .aab a Internal testing.
  4. Completar la sección App content.

Mientras la app de Android no se haya publicado nunca, pon release_status: draft en release.yml. Las cuentas de desarrollador personales nuevas también necesitan una prueba cerrada con 12 testers durante 14 días antes de pasar a producción.

Después, termina la primera publicación:

terminal
appship metadata --android
appship upload
appship submit

8Cada publicación posterior

Sube la versión y el número de build en tu proyecto y luego:

terminal
# pide a tu agente de IA que escriba las notas de versión (consulta Idiomas y notas de versión)
appship upload --build   # compila, luego TestFlight + track de Google Play (internal por defecto)
# prueba en TestFlight / el track internal
appship submit           # iOS: App Review · Android: promover a producción
appship status           # estado de la revisión y versiones en ambas tiendas

Para un despliegue gradual en Android:

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

Todos los comandos que escriben en una tienda piden confirmación antes. Añade --dry-run para ver exactamente qué se enviaría.

9Ejecútalo en CI

En CI, las claves provienen de secrets mediante variables de entorno APPSHIP_*, y todos los comandos de escritura necesitan --yes. Añade estos secrets al repositorio (en GitHub: Settings → Secrets and variables → Actions):

SecretValor
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYSalida de base64 -i AuthKey_XXX.p8
APPSHIP_PLAY_JSONSalida de base64 -i play-service-account.json
Secrets de firmaDependen de cómo firmes, por ejemplo MATCH_PASSWORD para fastlane match, o un keystore de Android en base64

Los pasos de publicación de un workflow de GitHub Actions:

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # los builds de iOS necesitan macOS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...tu toolchain, fastlane y la configuración de firma...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Añade tu propia configuración de Flutter, el paso de firma y, si quieres un disparador manual para submit, un input workflow_dispatch como el de arriba.

  • Crear la app de iOS y subir App Privacy requieren el Apple ID con 2FA. Hazlo una vez en tu máquina, no en CI.
  • Para fijar una versión de fastlane, usa un Gemfile y define APPSHIP_FASTLANE="bundle exec fastlane".
  • Prueba el pipeline de principio a fin con --dry-run antes de dejar que envíe nada.

Referencia

Firma

appship no compila ni firma tu app. Ejecuta tu build_command y recoge el artefacto firmado.

  • iOS: la configuración más sencilla es la firma automática en Xcode (Signing & Capabilities). Para equipos y CI, usa fastlane match.
  • Android: crea un keystore de subida, configura signingConfigs en Gradle y activa Play App Signing con la primera subida. Mantén el keystore fuera de git, por ejemplo en release/keys/, que está en gitignore.

Firma de iOS sin acceso de propietario

En iOS, firmar la app y subirla requieren cosas distintas, y ambas suelen estar en manos del Account Holder o de un Admin. appship sigue sin compilar ni firmar por ti. Audita los archivos que te han dado, los instala y pasa la configuración de firma a tu comando de build.

Tu situaciónFirmar conSubir con
Account Holder o AdminFirma automática, o fastlane matchClave de API de equipo
El propietario te envió los archivos de firma y una clave de API de equipoArchivos de ios.signingClave de API de equipo
El propietario te envió los archivos de firma, sin clave de APIArchivos de ios.signingTu propia clave de API individual
Ninguna clave de APIArchivos de ios.signingTransporter o Xcode Organizer, a mano
El propietario solo te envió una clave de APIPide un certificado y un perfil, o usa la firma automática de Xcode si tu rol lo permiteClave de API

Pide al propietario

  • Un certificado Apple Distribution como .p12, exportado desde Keychain Access con contraseña. Debe incluir la clave privada.
  • Un perfil de aprovisionamiento App Store (.mobileprovision) para cada bundle id, incluidas las app extensions.
  • Opcionalmente, una clave de API de equipo: .p8, Key ID e Issuer ID.

Para no tener que mover una clave privada de un sitio a otro, crea una solicitud de firma de certificado (CSR) en tu propio Mac y pide al propietario que emita el certificado a partir de ella. Así la clave privada nunca sale de tu máquina y no necesitas el .p12.

Configura e instala

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # instala los perfiles, importa el .p12
appship build --ios
appship doctor                                    # audita los perfiles, el keychain y el .ipa generado
appship upload --ios

La contraseña del .p12 nunca se guarda en release.yml; pásala en APPSHIP_P12_PASSWORD. El comando de build recibe $APPSHIP_EXPORT_OPTIONS (un ExportOptions.plist generado), $APPSHIP_IOS_BUNDLE_ID y $APPSHIP_IOS_TEAM_ID. Con fastlane gym usa --export_options "$APPSHIP_EXPORT_OPTIONS". El plist controla solo el paso de exportación; con firma manual, desactiva también la firma automática en el proyecto de Xcode para que el paso de archivado use el mismo perfil.

Qué comprueba doctor

  • Cada perfil es un perfil App Store de iOS, no ha caducado (advertencia si le quedan menos de 30 días), pertenece al equipo de ios.team_id y cubre ios.bundle_id.
  • El .p12 existe y no es legible por todos, y en el keychain hay un certificado que coincide, con su clave privada (solo macOS).
  • El .ipa generado está firmado para el bundle id correcto, con un perfil válido de ios.signing.profiles.
  • build_command realmente usa $APPSHIP_EXPORT_OPTIONS.

Sin clave de API de equipo

  • Clave individual: en App Store Connect, Integrations → Individual Keys. No tiene Issuer ID, así que deja issuer_id vacío: appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. Tiene los permisos de tu propio rol, y un Admin puede desactivar la función. Aún no se ha verificado con una cuenta real.
  • Ninguna clave: firma y compila de la misma forma, y luego sube el .ipa con Transporter o con Xcode → Organizer → Distribute App. doctor audita antes el archivo. appship no sube con un Apple ID, porque eso requiere 2FA interactiva.

En CI

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

Esto crea un keychain dedicado, de modo que el keychain de inicio de sesión del runner queda intacto. Los perfiles y certificados caducan tras aproximadamente un año; doctor avisa 30 días antes.

Los roles difieren en lo que pueden hacer; consulta la tabla de roles en la ayuda de App Store Connect. Las pantallas de Apple cambian, así que toma estos pasos como válidos a fecha de 09/2026.

De dónde se leen las claves

Para cada valor, gana la primera fuente que se encuentre. Puedes combinarlas, por ejemplo un perfil en tu máquina y variables de entorno en CI.

  1. Variables de entorno: APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH o APPSHIP_ASC_KEY (contenido, en texto plano o base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH o APPSHIP_PLAY_JSON, y APPSHIP_PROFILE.
  2. release/release.yml: rutas a archivos en release/keys/, que está en gitignore. El Key ID y el Issuer ID no son secretos y se pueden subir al repositorio.
  3. Un perfil: credentials.profile: my-company, que apunta a ~/.appship/credentials/my-company/.
release/release.yml, sin perfil
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # opcional
  android:
    json_key_path: release/keys/play-service-account.json

Si una clave llega a un commit

  1. Revócala de inmediato. iOS: App Store Connect → Integrations → Revoke. Android: Cloud Console → la cuenta de servicio → Keys → Delete.
  2. Crea una clave nueva y actualiza tu perfil o los secrets de CI.
  3. Ejecuta git rm --cached <file>. La clave permanece en el historial de git, por eso revocarla es el paso que importa.
