プロジェクトに appship を導入する

まだストアに一度も公開していないアプリから、App Review に提出済みのビルドまでを解説します。初回は約 1 時間を見込んでください。 その大半は、Apple と Google のコンソールでキーを取得する作業です。

早期リリース版です。 v0.2.0 はテストとドライランで検証済みですが、実際のストアに対してはまだ実行されていません。 ストアへ書き込むコマンドはすべて --dry-run に対応しています。まずは appship status などの読み取り専用コマンドから始めてください。

1必要なもの

必要なもの補足
Node.js 22 以降appship は npm パッケージです。
fastlaneappship はストアへのあらゆる呼び出しに fastlane を使います。お使いのマシンに合わせて、fastlane のドキュメントで推奨されている方法でインストールしてください。
Xcode を搭載した macOSiOS のビルドとアップロードにのみ必要です。Android のみのプロジェクトは Linux でも動作します。

2インストール

appship はマシンごとに 1 回、グローバルにインストールします。アプリの package.json には何も追加されません。

terminal
npm i -g appship-ai
appship --version

パッケージ名は appship-ai で、インストールされるコマンドは appship です。インストールせずに試すには、npx appship-ai --help を実行してください。

3ストアキーを取得する

この作業は、プロジェクトごとではなくデベロッパーアカウントごとに 1 回行います。どちらのキーもあなたの名義でビルドを公開できるため、git には絶対にコミットしないでください。

iOS: App Store Connect API キー

  1. App Store Connect で Users and Access → Integrations → App Store Connect API を開きます。
  2. Team Keys の下にある + をクリックします。名前を appship にして、App Manager ロールを付与します。
  3. AuthKey_XXXXXXXXXX.p8 をダウンロードします。Apple はダウンロードを 1 回しか許可しません。
  4. Key ID（10 文字。ファイル名にも含まれます）と Issuer ID（キー一覧の上に表示される UUID）を控えます。

Team Keys を作成できるのは Account Holder または Admin だけです。該当しない場合は、オーナーにキーの送付を依頼するか、個人用キーについて オーナー権限なしでの iOS 署名 を参照してください。

Apple ID（メールアドレス）は任意です。アプリレコードの作成と App Privacy の回答のアップロードにのみ必要で、Apple の API キーではどちらもできないためです。2FA が必要なので、CI では使えません。

Android: Google Play サービスアカウント

  1. Google Cloud Console でプロジェクトを選び、Google Play Android Developer API を有効にします。
  2. IAM & Admin → Service Accounts → Create service account に進みます。GCP のロールは不要です。
  3. アカウントを開き、Keys → Add key → JSON でキーファイルをダウンロードします。
  4. Play Console の Users and permissions → Invite new users で、JSON 内の client_email を招待します。Release apps to testing tracks、Release to production、Manage store presence の権限を付与してください。
  5. 権限が反映されるまで数分待ちます。新しいアカウントでは最大 24 時間かかることがあります。

プロファイルとして保存する

プロファイルは、キーを権限 600 で ~/.appship/credentials/<name>/ にコピーします。これにより、このマシン上のすべてのプロジェクトで同じキーを共有できます。フラグを付けずに実行すると、対話形式で順に質問されます。

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4プロジェクトをセットアップする

アプリのリポジトリのルートで init を実行します。

terminal
cd ~/Projects/my-app
appship init --profile my-company

init は Flutter、React Native、Cocos Creator、ネイティブのいずれのプロジェクトかを検出し、バンドル ID とパッケージ名を読み取って、ビルドコマンドと成果物のパスを設定します。次のフォルダを作成し、release/keys/* と release/.appship/ を .gitignore に追加します。

project layout
my-app/
└── release/
    ├── release.yml            # ID、成果物、ビルドコマンド、トラック、認証情報
    ├── questionnaire.yml      # ストアの質問への回答
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # gitignore 対象。プロファイルを使わない場合のみ
    └── .appship/              # gitignore 対象。fastlane 用の一時ファイル

release/release.yml を開き、各プラットフォームの artifact と build_command を確認します。Flutter アプリの場合は次のようになります。

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # Apple の承認後すぐにリリースする
    phased_release: false      # 7 日間の段階的リリース
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # アプリが未公開の間は draft
  rollout: 1                   # 0.2 = 20% の段階的ロールアウト
credentials:
  profile: my-company

keys/ と .appship/ を除く release/ フォルダ全体をコミットしてください。リポジトリに Fastfile は追加されません。リリースのロジックは appship 側に残るため、appship を更新すればすべてのプロジェクトが更新されます。

5ストア掲載情報を入力する

アプリがすでに公開されている場合は、手で入力せずに現在の掲載情報を取得します。

terminal
appship metadata pull

そうでない場合は、次のファイルにあるすべての TODO を置き換えてください。

  • release/questionnaire.yml: 年齢レーティング、輸出コンプライアンス、コンテンツの権利、審査担当者の連絡先、App Privacy、および Android の「アプリのコンテンツ」の回答。
  • テキスト: release/ios/metadata/<locale>/*.txt と release/android/metadata/<locale>/*.txt。
  • 言語ごとのリリースノート: ロケールごとに 1 つのフォルダ。下の言語とリリースノートを参照してください。
  • iOS のスクリーンショット（release/ios/screenshots/<locale>/）: iPhone 6.9 インチ（1320×2868）または 6.5 インチ（1284×2778）のセットを少なくとも 1 つ。
  • Android の画像（release/android/metadata/<locale>/images/）: 512×512 の icon.png、1024×500 の featureGraphic.png、および phoneScreenshots/ に少なくとも 2 枚の画像。

言語とリリースノート

どちらのストアも、言語ごとに個別の「新機能」テキストを受け付けます。言語ごとに 1 つのフォルダを作り、各フォルダに専用のリリースノートを置きます。

ストアファイル（ロケールのフォルダごとに 1 つ）上限
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 文字
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 文字

言語を追加するには、次の手順を行います。

  1. release.yml に言語を記載します。このリストは任意で、省略した場合は appship が見つかったすべてのフォルダを使用します。iOS と Android ではロケールコードが異なるため、プラットフォームごとに別のリストを持ちます。
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # Play のコードは異なります。例: ここでは zh-CN、iOS では zh-Hans
  2. release/ios/metadata/vi/ のようにフォルダを作成し、必須ファイルを入力します。iOS では name.txt、description.txt、keywords.txt、support_url.txt、privacy_url.txt、release_notes.txt、Android では title.txt、short_description.txt、full_description.txt、changelogs/default.txt です。
  3. iOS のスクリーンショットを release/ios/screenshots/<locale>/ に追加します。Android の場合は、先に Play Console でその言語を有効にしてください。
  4. appship doctor を実行します。リストにあるのにフォルダがないロケールはエラーになります。リストにないフォルダは、ストアにそのままプッシュされるため警告になります。

知っておくべきこと:

  • App Store Connect で先に言語を追加する必要はありません。メタデータをプッシュした時点で作成されます。
  • アプリの最初のバージョンでは release_notes.txt を空のままにしてください。Apple はバージョン 1.0 のリリースノートを受け付けません。
  • リリースノートのないロケールでは、その言語の「新機能」が空で表示されます。一部のロケールにだけノートがある場合は、doctor が警告します。
  • iOS のフォルダ名は、en-US、vi、ja、ko、de-DE、fr-FR、es-ES、pt-BR、zh-Hans、zh-Hant など、Apple のコードのいずれかである必要があります。zh-CN など、それ以外は doctor が拒否します。
  • fastlane の共有 default フォルダにはまだ対応していません。

おすすめの言語

次にどの言語を追加すべきか迷っていませんか？ appship は、利用者の多い 6 つの言語を提案します。スペイン語（スペインとラテンアメリカ）、ブラジルポルトガル語、ドイツ語、フランス語、日本語、韓国語です。2 つのストアではコードが異なります。

言語--locales の IDiOS のフォルダAndroid のフォルダ
スペイン語（スペイン）eses-ESes-ES
スペイン語（ラテンアメリカ）eses-MXes-419
ポルトガル語（ブラジル）pt-BRpt-BRpt-BR
ドイツ語dede-DEde-DE
フランス語frfr-FRfr-FR
日本語jajaja-JP
韓国語kokoko-KR
  • フォルダはプロジェクトのセットアップ時に作成できます。6 言語すべてなら appship init --locales preset、一部だけなら --locales es,ja を使います。各プラットフォームに正しいコードで locales を書き込み、翻訳用に TODO で埋めた掲載情報ファイルを作成します。すべての TODO を置き換えるまで、doctor は失敗します。
  • すでにあるプロジェクトでは、上記のコードを使って手作業でフォルダを追加してください（init --force は release.yml を書き換えてしまいます）。
  • スペイン語は、実際に書くバリエーションだけを残してください。iOS の es-MX と Play の es-419 で、ラテンアメリカ全体をカバーできます。
  • ストアの上限はバイト数や単語数ではなく、文字数で数えます。日本語や韓国語のテキストは通常、英語より短くなります。ドイツ語とフランス語は長くなりやすく、30 文字のタイトル上限にかかることがよくあります。
  • アップロードの前に、Play Console で各言語を有効にしてください。Play の言語コードではない Android のフォルダがあると doctor が警告し、修正案を示します。たとえば ja は ja-JP にすべきです。
  • release-notes スキルは、各言語の慣習を把握しています。敬体・常体などの文体、地域ごとのバリエーション、日本語の全角句読点、? ! : ; の前に入れるフランス語のスペースなどです。

AI コーディングエージェントでリリースノートを書く

appship init は、AI コーディングエージェント（Claude Code、Codex、Antigravity）向けのスキル release-notes をインストールします。Claude Code 用は .claude/skills/、Codex と Antigravity 用は .agents/skills/ に置かれます。リリースの前に、エージェントに「このバージョンのリリースノートを書いて」と頼みます（Claude Code では /release-notes、Codex では $release-notes を実行することもできます）。エージェントは次の処理を行います。

  1. release.yml とロケールのフォルダを読み込みます。
  2. 前回のタグ以降の git log を読み込みます。CHANGELOG.md がある場合はそれも読みます。
  3. ユーザー向けの短いノートをプライマリ言語で書き、他のすべてのロケールに翻訳します。
  4. ストアの上限に収め、ファイルを書き込んでから appship doctor を実行します。

ノートは通常のファイルのままなので、確認や編集ができます。スキルは、すでにあるテキストを上書きする前に確認し、ストアには何もプッシュしません。

AI エージェントでスクリーンショットとストアの申告を作成する

init は、その隣にさらに 2 つのスキルをインストールします。release-notes と同様に、これらは release/ 内のファイルを書き込み、appship doctor を実行するだけで、プッシュはあなたに任せます。

  • store-screenshots：撮影する画面をあなたと一緒に計画し、iOS シミュレータまたは Android エミュレータから撮影して、言語ごとに翻訳した見出しを追加し、すべての画像を各ストアが受け付けるサイズで書き出します（iPhone 6.9" 1320×2868、アプリが iPad で動作する場合は iPad 13"、Play 1080×1920）。Play のアイコンとフィーチャーグラフィックも作成します。
  • app-content：依存関係、権限、コードをもとに release/questionnaire.yml（年齢レーティング、App Privacy、輸出コンプライアンス、データセーフティ、コンテンツのレーティング、ターゲットユーザー、広告、アプリへのアクセス）を埋め、コードからはわからない点はあなたに質問し、2 つのストア間で回答の整合性を保ちます。
エージェントスキルのフォルダ実行方法
Claude Code.claude/skills//store-screenshots
Codex.agents/skills/$store-screenshots または /skills
Antigravity.agents/skills/「use the store-screenshots skill」と頼みます

appship 自体が AI を呼び出すことはありません。プロジェクトのルートでエージェントを開き、ご自身のアカウントでサインインして、エージェントが実行を求めるコマンドを承認してください。

エージェントは init の実行時に選べます。あとからスキルをインストールする場合や、appship のアップグレード後にスキルを更新する場合は、次のコマンドを使います。

terminal
appship init --agents all             # Claude Code、Codex、Antigravity 用のスキル
appship skills                        # 各エージェントにあるスキル
appship skills add --agent codex      # Codex / Antigravity 用にインストール（.agents/skills/）
appship skills add --force            # このバージョンのもので置き換え

6doctor で確認する

doctor は、ツール、設定、キー、成果物、文字数の上限、画像サイズ、プレースホルダのテキストを確認し、キーファイルが git で追跡されていると失敗します。✗ がなくなるまで繰り返してください。! は警告で、リリースを妨げません。

7初回リリース

terminal
appship build
appship first-release --create-app
  • iOS: App Store Connect にアプリを作成し（Apple ID が必要で、2FA コードを求められる場合があります）、続けて掲載情報、スクリーンショット、年齢レーティング、審査情報、App Privacy をプッシュします。
  • Android: Google Play にはアプリを作成する API がないため、appship は代わりに手順を表示します。
  • どちらも release/CHECKLIST.md を書き出します。手作業で行う必要のあるコンソール上の手順が載っており、questionnaire.yml の回答をそのままコピーできる形で入っています。

Google Play では、チェックリストに従って次を行います。

  1. Play Console でアプリを作成します。
  2. サービスアカウントをアプリに招待します。
  3. 最初の .aab を手作業で内部テストにアップロードします。
  4. 「アプリのコンテンツ」セクションを入力します。

Android アプリが一度も公開されていない間は、release.yml で release_status: draft を設定してください。新規の個人デベロッパーアカウントでは、本番公開の前に、12 人のテスターによるクローズドテストを 14 日間行う必要もあります。

そのうえで、初回リリースを完了させます。

terminal
appship metadata --android
appship upload
appship submit

82 回目以降のリリース

プロジェクトのバージョンとビルド番号を上げてから、次を実行します。

terminal
# AI エージェントにリリースノートを書いてもらう（「言語とリリースノート」を参照）
appship upload --build   # ビルドしてから TestFlight と Google Play のトラックへ（デフォルトは internal）
# TestFlight / internal トラックでテストする
appship submit           # iOS: App Review へ提出 · Android: production へ昇格
appship status           # 両ストアの審査状況とバージョン

Android で段階的ロールアウトを行う場合は次のとおりです。

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

ストアへ書き込むコマンドは、すべて事前に確認を求めます。--dry-run を付けると、実際に送信される内容を正確に確認できます。

9CI で実行する

CI では、キーはシークレットから APPSHIP_* 環境変数を通じて渡され、書き込みコマンドにはすべて --yes が必要です。次のリポジトリシークレットを追加してください（GitHub では Settings → Secrets and variables → Actions）。

シークレット値
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYbase64 -i AuthKey_XXX.p8 の出力
APPSHIP_PLAY_JSONbase64 -i play-service-account.json の出力
署名用シークレット署名方法によって異なります。たとえば fastlane match なら MATCH_PASSWORD、Android なら base64 化したキーストアです

GitHub Actions ワークフローのリリース手順:

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # iOS のビルドには macOS が必要
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...お使いのツールチェーン、fastlane、署名のセットアップ...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Flutter のセットアップと署名の手順は、ご自身のものを追加してください。submit を手動で起動したい場合は、上記のような workflow_dispatch の入力も追加します。

  • iOS アプリの作成と App Privacy のアップロードには、2FA が必要な Apple ID が要ります。これらは CI ではなく、手元のマシンで 1 回だけ行ってください。
  • fastlane のバージョンを固定するには、Gemfile を使い、APPSHIP_FASTLANE="bundle exec fastlane" を設定します。
  • 何かをプッシュさせる前に、--dry-run でパイプラインを最初から最後まで試してください。

リファレンス

署名

appship はアプリのビルドも署名も行いません。build_command を実行し、署名済みの成果物を取得するだけです。

  • iOS: もっとも簡単なのは、Xcode の自動署名（Signing & Capabilities）です。チームや CI では、fastlane match を使います。
  • Android: アップロード用キーストアを作成し、Gradle の signingConfigs を設定して、最初のアップロード時に Play App Signing を有効にします。キーストアは git に含めないでください。たとえば、gitignore 対象の release/keys/ に置きます。

オーナー権限なしでの iOS 署名

iOS では、アプリの署名とアップロードに必要なものが異なり、どちらも通常は Account Holder または Admin が持っています。それでも appship がビルドや署名を代行することはありません。受け取ったファイルを検証し、インストールし、署名設定をビルドコマンドに渡します。

状況署名方法アップロード方法
Account Holder または Admin自動署名、または fastlane matchTeam API キー
オーナーから署名ファイルと Team API キーを受け取ったios.signing のファイルTeam API キー
オーナーから署名ファイルを受け取ったが、API キーはないios.signing のファイル自分の Individual API キー
API キーがまったくないios.signing のファイルTransporter または Xcode Organizer で手作業
オーナーから API キーだけを受け取った証明書とプロファイルを依頼するか、ロールが許せば Xcode の自動署名API キー

オーナーに依頼するもの

  • Apple Distribution 証明書。キーチェーンアクセスからパスワード付きで書き出した .p12 です。秘密鍵を含めておく必要があります。
  • 各バンドル ID（アプリ拡張を含む）用の App Store プロビジョニングプロファイル（.mobileprovision）。
  • 必要に応じて Team API キー: .p8、Key ID、Issuer ID。

秘密鍵をやり取りしないためには、自分の Mac で証明書署名リクエストを作成し、オーナーにそれをもとに証明書を発行してもらいます。こうすれば秘密鍵はマシンの外に出ず、.p12 も不要になります。

設定とインストール

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # プロファイルをインストールし、.p12 をインポート
appship build --ios
appship doctor                                    # プロファイル、キーチェーン、ビルド済みの .ipa を検証
appship upload --ios

.p12 のパスワードは release.yml には保存されません。APPSHIP_P12_PASSWORD で渡してください。ビルドコマンドには、$APPSHIP_EXPORT_OPTIONS（生成された ExportOptions.plist）、$APPSHIP_IOS_BUNDLE_ID、$APPSHIP_IOS_TEAM_ID が渡されます。fastlane gym では --export_options "$APPSHIP_EXPORT_OPTIONS" を使います。この plist が制御するのはエクスポートの手順だけです。手動署名の場合は、アーカイブの手順でも同じプロファイルが使われるよう、Xcode プロジェクトで自動署名もオフにしてください。

doctor が確認する内容

  • 各プロファイルが iOS の App Store プロファイルであること、有効期限が切れていないこと（30 日未満なら警告）、ios.team_id のチームのものであること、そして ios.bundle_id をカバーしていること。
  • .p12 が存在し、他のユーザーから読み取れないこと。また、対応する証明書と秘密鍵がキーチェーンにあること（macOS のみ）。
  • ビルド済みの .ipa が正しいバンドル ID で署名され、ios.signing.profiles の有効なプロファイルが使われていること。
  • build_command が実際に $APPSHIP_EXPORT_OPTIONS を使っていること。

Team API キーがない場合

  • Individual キー: App Store Connect の Integrations → Individual Keys で作成します。Issuer ID はないため、issuer_id は空のままにします: appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX。このキーには自分のロールの権限が付き、Admin はこの機能をオフにできます。実際のアカウントではまだ検証していません。
  • キーがまったくない場合: 同じ方法で署名とビルドを行い、.ipa を Transporter または Xcode → Organizer → Distribute App でアップロードします。doctor は、その前にファイルを検証します。appship は Apple ID ではアップロードしません。対話的な 2FA が必要になるためです。

CI の場合

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

専用のキーチェーンが作成されるため、ランナーのログインキーチェーンには影響しません。プロファイルと証明書は約 1 年で期限切れになります。doctor は 30 日前に警告します。

ロールごとに実行できる操作は異なります。App Store Connect ヘルプのロール表を確認してください。Apple の画面は変更されるため、この手順は 2026 年 9 月時点のものとして扱ってください。

キーの読み込み元

値ごとに、最初に見つかった読み込み元が優先されます。組み合わせて使うこともできます。たとえば、手元のマシンではプロファイル、CI では環境変数、といった具合です。

  1. 環境変数: APPSHIP_ASC_KEY_ID、APPSHIP_ASC_ISSUER_ID、APPSHIP_ASC_KEY_PATH または APPSHIP_ASC_KEY（内容。プレーンテキストまたは base64）、APPSHIP_APPLE_ID、APPSHIP_PLAY_JSON_PATH または APPSHIP_PLAY_JSON、そして APPSHIP_PROFILE。
  2. release/release.yml: gitignore 対象の release/keys/ 内のファイルへのパス。Key ID と Issuer ID は秘密情報ではないため、コミットできます。
  3. プロファイル: credentials.profile: my-company で、~/.appship/credentials/my-company/ を指定します。
release/release.yml、プロファイルなしの場合
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # 任意
  android:
    json_key_path: release/keys/play-service-account.json

キーをコミットしてしまった場合

  1. ただちに無効化してください。 iOS: App Store Connect → Integrations → Revoke。Android: Cloud Console → 該当のサービスアカウント → Keys → Delete。
  2. 新しいキーを作成し、プロファイルまたは CI のシークレットを更新します。
  3. git rm --cached <file> を実行します。キーは git の履歴に残るため、無効化こそが重要な手順です。
