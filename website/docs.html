Integration guide · v0.2.0

Add appship to your project

From an app that has never been on the stores to a build in App Review. Plan for about an hour the first time, most of it spent in the Apple and Google consoles getting keys.

2Install

Install appship once per machine, globally. Nothing gets added to your app's package.json.

terminal
npm i -g appship-ai
appship --version

The package is called appship-ai and installs the appship command. To try it without installing, run npx appship-ai --help.

3Get store keys

You do this once per developer account, not per project. Both keys can publish builds under your name, so never commit them to git.

iOS: App Store Connect API key

  1. In App Store Connect, open Users and Access → Integrations → App Store Connect API.
  2. Under Team Keys, click +. Name it appship and give it the App Manager role.
  3. Download AuthKey_XXXXXXXXXX.p8. Apple lets you download it only once.
  4. Note the Key ID (10 characters, also in the file name) and the Issuer ID (the UUID above the key table).

Team Keys can only be created by an Account Holder or Admin. If that isn't you, ask the owner to send the key, or see iOS signing without owner access for an individual key.

An Apple ID (email) is optional. It is only needed to create the app record and upload App Privacy answers, because Apple's API key can't do either. It needs 2FA, so it never works in CI.

Android: Google Play service account

  1. In Google Cloud Console, pick a project and enable the Google Play Android Developer API.
  2. Go to IAM & Admin → Service Accounts → Create service account. It needs no GCP role.
  3. Open the account, then Keys → Add key → JSON to download the key file.
  4. In Play Console, go to Users and permissions → Invite new users and invite the client_email from the JSON. Grant Release apps to testing tracks, Release to production and Manage store presence.
  5. Wait a few minutes for the permissions to apply. On a new account it can take up to 24 hours.

Save them as a profile

A profile copies the keys to ~/.appship/credentials/<name>/ with mode 600, so every project on this machine can share them. Run it without flags to be asked step by step.

terminal
appship credentials add my-company \
  --asc-key ~/Downloads/AuthKey_ABC123DEFG.p8 \
  --asc-key-id ABC123DEFG \
  --asc-issuer-id 69a6de7a-0000-0000-0000-000000000000 \
  --play-json ~/Downloads/play-service-account.json

appship credentials list

4Set up the project

Run init from the root of your app repo.

terminal
cd ~/Projects/my-app
appship init --profile my-company

init detects Flutter, React Native, Cocos Creator or native projects, reads your bundle id and package name, and fills in the build command and artifact path. It creates this folder and adds release/keys/* and release/.appship/ to .gitignore:

project layout
my-app/
└── release/
    ├── release.yml            # ids, artifacts, build commands, tracks, credentials
    ├── questionnaire.yml      # answers to store questions
    ├── ios/metadata/<locale>/*.txt
    ├── ios/screenshots/<locale>/*.png
    ├── android/metadata/<locale>/{*.txt, images/}
    ├── keys/                  # gitignored; only if you don't use a profile
    └── .appship/              # gitignored; scratch files for fastlane

Open release/release.yml and check artifact and build_command for each platform. For a Flutter app it looks like this:

release/release.yml
app:
  name: "My App"
  primary_locale: en-US
ios:
  bundle_id: com.example.myapp
  artifact: "build/ios/ipa/*.ipa"
  build_command: "flutter build ipa --release"
  upload_screenshots: true
  submit:
    automatic_release: false   # release as soon as Apple approves
    phased_release: false      # 7-day phased rollout
android:
  package_name: com.example.myapp
  artifact: "build/app/outputs/bundle/release/*.aab"
  build_command: "flutter build appbundle --release"
  track: internal              # internal | alpha | beta | production
  release_status: completed    # draft while the app is unpublished
  rollout: 1                   # 0.2 = 20% staged rollout
credentials:
  profile: my-company

Commit the whole release/ folder except keys/ and .appship/. Your repo gets no Fastfile: the release logic stays in appship, so updating appship updates every project.

5Fill in the listing

If the app is already live, pull the current listing instead of typing it:

terminal
appship metadata pull

Otherwise, replace every TODO in these files:

  • release/questionnaire.yml: age rating, export compliance, content rights, reviewer contact, App Privacy, and the Android App content answers.
  • Text: release/ios/metadata/<locale>/*.txt and release/android/metadata/<locale>/*.txt.
  • Release notes per language: one folder per locale. See Languages and release notes below.
  • iOS screenshots in release/ios/screenshots/<locale>/: at least one iPhone 6.9" set (1320×2868) or 6.5" set (1284×2778).
  • Android images in release/android/metadata/<locale>/images/: icon.png 512×512, featureGraphic.png 1024×500, and at least 2 images in phoneScreenshots/.

Languages and release notes

Both stores take a separate "What's New" text for every language. Each language is a folder, and each folder holds its own release notes:

StoreFile, one per locale folderMax
App Storerelease/ios/metadata/<locale>/release_notes.txt4000 characters
Google Playrelease/android/metadata/<locale>/changelogs/default.txt500 characters

To add a language:

  1. List it in release.yml. The list is optional; without it appship uses every folder it finds. iOS and Android use different locale codes, so each platform has its own list:
    release/release.yml
    ios:
  locales: [en-US, vi, ja]
android:
  locales: [en-US, vi, ja-JP]   # Play codes differ, e.g. zh-CN here, zh-Hans on iOS
  2. Create the folder, for example release/ios/metadata/vi/, and fill in the required files: name.txt, description.txt, keywords.txt, support_url.txt, privacy_url.txt and release_notes.txt on iOS; title.txt, short_description.txt, full_description.txt and changelogs/default.txt on Android.
  3. Add iOS screenshots to release/ios/screenshots/<locale>/. Enable the language in Play Console first for Android.
  4. Run appship doctor. A listed locale with no folder is an error. A folder that is not listed is a warning, because it is still pushed to the store.

Things to know:

  • You don't need to add the language in App Store Connect first. It is created when the metadata is pushed.
  • Leave release_notes.txt empty for the very first version of an app. Apple does not accept release notes on version 1.0.
  • A locale without release notes shows an empty "What's New" in that language. doctor warns when some locales have notes and others don't.
  • iOS folder names must be one of Apple's codes, such as en-US, vi, ja, ko, de-DE, fr-FR, es-ES, pt-BR, zh-Hans or zh-Hant. doctor rejects anything else, for example zh-CN.
  • fastlane's shared default folder is not supported yet.

Suggested languages

Not sure which languages to add next? appship suggests six with large audiences: Spanish (Spain and Latin America), Brazilian Portuguese, German, French, Japanese and Korean. The two stores use different codes:

Language--locales idiOS folderAndroid folder
Spanish, Spaineses-ESes-ES
Spanish, Latin Americaeses-MXes-419
Portuguese, Brazilpt-BRpt-BRpt-BR
Germandede-DEde-DE
Frenchfrfr-FRfr-FR
Japanesejajaja-JP
Koreankokoko-KR
  • Create the folders when you set up a project: appship init --locales preset for all six, or --locales es,ja for some. It writes locales for each platform with the right codes and creates listing files filled with TODO for you to translate. doctor fails until every TODO is replaced.
  • For a project that already exists, add the folders by hand with the codes above (init --force would rewrite release.yml).
  • Keep only the Spanish variant you will really write. es-MX on iOS and es-419 on Play cover all of Latin America.
  • Store limits count characters, not bytes or words. Japanese and Korean text is usually shorter than English; German and French run longer and often hit the 30-character title limit.
  • Enable each language in Play Console before uploading. doctor warns about an Android folder that is not a Play language code and suggests the fix, for example ja should be ja-JP.
  • The release-notes skill knows each language's conventions: formal or informal address, regional variants, Japanese full-width punctuation and French spacing before ? ! : ;.

Write release notes with an AI coding agent

appship init installs a skill, release-notes, for your AI coding agent (Claude Code, Codex or Antigravity): into .claude/skills/ for Claude Code, .agents/skills/ for Codex and Antigravity. Before a release, ask the agent to "write the release notes for this version" (or run /release-notes in Claude Code, $release-notes in Codex). It will:

  1. Read release.yml and the locale folders.
  2. Read git log since the last tag, and CHANGELOG.md if you have one.
  3. Write short, user-facing notes in your primary language and translate them into every other locale.
  4. Fit the store limits, write the files, then run appship doctor.

The notes stay plain files, so you can review and edit them. The skill asks before overwriting text that is already there, and it never pushes anything to a store.

Screenshots and store declarations with an AI agent

init installs two more skills next to it. Like release-notes, they only write files in release/, run appship doctor, and leave pushing to you.

  • store-screenshots: plans the shots with you, captures them from the iOS Simulator or an Android emulator, adds a translated headline per language, and renders every image at a size each store accepts (iPhone 6.9" 1320×2868, iPad 13" when the app runs on iPad, Play 1080×1920), plus the Play icon and feature graphic.
  • app-content: fills release/questionnaire.yml (age rating, App Privacy, export compliance, Data safety, content rating, target audience, ads, app access) from your dependencies, permissions and code, asks you what the code cannot show, and keeps the answers consistent between the two stores.
AgentSkill folderHow to run
Claude Code.claude/skills//store-screenshots
Codex.agents/skills/$store-screenshots or /skills
Antigravity.agents/skills/ask "use the store-screenshots skill"

appship never calls an AI itself. Open the agent at the project root, signed in with your own account, and approve the commands it asks to run.

Choose the agents when you run init, or install and update the skills later, for example after upgrading appship:

terminal
appship init --agents all             # skills for Claude Code, Codex and Antigravity
appship skills                        # which skills each agent has
appship skills add --agent codex      # install for Codex / Antigravity (.agents/skills/)
appship skills add --force            # replace them with this version

6Check with doctor

doctor checks tools, config, keys, artifacts, character limits, image sizes and placeholder text, and fails if a key file is tracked by git. Repeat until there are no ✗. A ! is a warning and does not block a release.

appship doctor
▸ Security
  ✓ No key files tracked by git
  ✓ .gitignore protects release/keys/
▸ iOS · store listing
  ✗ ios/metadata/en-US/subtitle.txt is 34 characters (max 30)
▸ Android · store listing
  ✓ Metadata OK for en-US

  ✗ 1 error(s), 0 warning(s)

7First release

terminal
appship build
appship first-release --create-app
  • iOS: creates the app in App Store Connect (needs the Apple ID and may ask for a 2FA code), then pushes the listing, screenshots, age rating, review info and App Privacy.
  • Android: Google Play has no API to create an app, so appship prints the steps instead.
  • Both write release/CHECKLIST.md: the console steps that must be done by hand, with your answers from questionnaire.yml ready to copy.

On Google Play, follow the checklist to:

  1. Create the app in Play Console.
  2. Invite the service account to the app.
  3. Upload the first .aab by hand to Internal testing.
  4. Fill in the App content section.

While the Android app has never been published, set release_status: draft in release.yml. New personal developer accounts also need a closed test with 12 testers for 14 days before production.

Then finish the first release:

terminal
appship metadata --android
appship upload
appship submit

8Every release after

Bump the version and build number in your project, then:

terminal
# ask your AI agent to write the release notes (see Languages and release notes)
appship upload --build   # build, then TestFlight + Google Play track (internal by default)
# test on TestFlight / the internal track
appship submit           # iOS: App Review · Android: promote to production
appship status           # review state and versions on both stores

For a staged rollout on Android:

terminal
appship submit --android --rollout 10%
appship promote --from production --to production --rollout 50%
appship promote --from production --to production --rollout 100%

Every command that writes to a store asks for confirmation first. Add --dry-run to see exactly what would be sent.

9Run it in CI

In CI, keys come from secrets through APPSHIP_* environment variables, and every write command needs --yes. Add these repository secrets (in GitHub: Settings → Secrets and variables → Actions):

SecretValue
APPSHIP_ASC_KEY_IDKey ID
APPSHIP_ASC_ISSUER_IDIssuer ID
APPSHIP_ASC_KEYOutput of base64 -i AuthKey_XXX.p8
APPSHIP_PLAY_JSONOutput of base64 -i play-service-account.json
Signing secretsDepends on how you sign, for example MATCH_PASSWORD for fastlane match, or an Android keystore in base64

The release steps of a GitHub Actions workflow:

.github/workflows/release.yml
env:
  APPSHIP_ASC_KEY_ID: ${{ secrets.APPSHIP_ASC_KEY_ID }}
  APPSHIP_ASC_ISSUER_ID: ${{ secrets.APPSHIP_ASC_ISSUER_ID }}
  APPSHIP_ASC_KEY: ${{ secrets.APPSHIP_ASC_KEY }}
  APPSHIP_PLAY_JSON: ${{ secrets.APPSHIP_PLAY_JSON }}

jobs:
  release:
    runs-on: macos-latest     # iOS builds need macOS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      # ...your toolchain, fastlane and signing setup...
      - run: npm i -g appship-ai
      - run: appship doctor --skip-artifacts
      - run: appship upload --build --yes
      - if: ${{ inputs.submit }}
        run: appship submit --yes

Add your own Flutter setup, signing step and, if you want a manual trigger for submit, a workflow_dispatch input like the one above.

  • Creating the iOS app and uploading App Privacy need the Apple ID with 2FA. Do those once on your machine, not in CI.
  • To pin a fastlane version, use a Gemfile and set APPSHIP_FASTLANE="bundle exec fastlane".
  • Try the pipeline end to end with --dry-run before letting it push anything.

Reference

Signing

appship doesn't build or sign your app. It runs your build_command and picks up the signed artifact.

  • iOS: the simplest setup is Automatic signing in Xcode (Signing & Capabilities). For teams and CI, use fastlane match.
  • Android: create an upload keystore, configure signingConfigs in Gradle, and turn on Play App Signing with the first upload. Keep the keystore out of git, for example in the gitignored release/keys/.

iOS signing without owner access

On iOS, signing the app and uploading it need different things, and both are usually held by the Account Holder or an Admin. appship still doesn't build or sign for you. It audits the files you were given, installs them, and passes the signing setup to your build command.

Your situationSign withUpload with
Account Holder or AdminAutomatic signing, or fastlane matchTeam API key
Owner sent signing files and a team API keyios.signing filesTeam API key
Owner sent signing files, no API keyios.signing filesYour own individual API key
No API key at allios.signing filesTransporter or Xcode Organizer, by hand
Owner sent only an API keyAsk for a certificate and profile, or Xcode automatic signing if your role allows itAPI key

Ask the owner for

  • An Apple Distribution certificate as .p12, exported from Keychain Access with a password. It must include the private key.
  • An App Store provisioning profile (.mobileprovision) for each bundle id, including app extensions.
  • Optionally a team API key: .p8, Key ID and Issuer ID.

To avoid moving a private key around, create a certificate signing request on your own Mac and have the owner issue the certificate from it. Then the private key never leaves your machine, and you don't need the .p12.

Configure and install

release/release.yml
ios:
  bundle_id: com.example.app
  team_id: ABCDE12345
  build_command: 'flutter build ipa --release --export-options-plist="$APPSHIP_EXPORT_OPTIONS"'
  signing:
    style: manual
    certificate: release/keys/AppleDistribution.p12
    profiles: [release/keys/AppStore.mobileprovision]
terminal
APPSHIP_P12_PASSWORD=... appship signing import   # install profiles, import the .p12
appship build --ios
appship doctor                                    # audit the profiles, keychain and the built .ipa
appship upload --ios

The .p12 password is never stored in release.yml; pass it in APPSHIP_P12_PASSWORD. The build command receives $APPSHIP_EXPORT_OPTIONS (a generated ExportOptions.plist), $APPSHIP_IOS_BUNDLE_ID and $APPSHIP_IOS_TEAM_ID. For fastlane gym use --export_options "$APPSHIP_EXPORT_OPTIONS". The plist controls the export step only; with manual signing, also turn off automatic signing in the Xcode project so the archive step uses the same profile.

What doctor checks

  • Each profile is an iOS App Store profile, not expired (a warning under 30 days), from the team in ios.team_id, and covers ios.bundle_id.
  • The .p12 exists and is not world-readable, and a matching certificate with its private key is in the keychain (macOS only).
  • The built .ipa is signed for the right bundle id, with a valid profile from ios.signing.profiles.
  • build_command actually uses $APPSHIP_EXPORT_OPTIONS.

No team API key

  • Individual key: in App Store Connect, Integrations → Individual Keys. It has no Issuer ID, so leave issuer_id empty: appship credentials add my-key --asc-key AuthKey_XXX.p8 --asc-key-id XXXXXXXXXX. It carries your own role's permissions, and an Admin can turn the feature off. Not yet verified against a real account.
  • No key at all: sign and build the same way, then upload the .ipa with Transporter or Xcode → Organizer → Distribute App. doctor still audits the file first. appship doesn't upload with an Apple ID, since that needs interactive 2FA.

In CI

GitHub Actions steps
- run: |
    mkdir -p release/keys
    echo "$P12_B64"     | base64 --decode > release/keys/AppleDistribution.p12
    echo "$PROFILE_B64" | base64 --decode > release/keys/AppStore.mobileprovision
  env: { P12_B64: ${{ secrets.IOS_DIST_P12_BASE64 }}, PROFILE_B64: ${{ secrets.IOS_PROFILE_BASE64 }} }
- run: appship signing import --yes --keychain "$RUNNER_TEMP/appship.keychain-db"
  env:
    APPSHIP_P12_PASSWORD: ${{ secrets.IOS_DIST_P12_PASSWORD }}
    APPSHIP_KEYCHAIN_PASSWORD: ${{ secrets.KEYCHAIN_PASSWORD }}

This creates a dedicated keychain, so the runner's login keychain is untouched. Profiles and certificates expire after about a year; doctor warns 30 days before.

Roles differ in what they may do; check the role table in App Store Connect Help. Apple's screens change, so treat the steps as of 09/2026.

Where keys are read from

For each value, the first source found wins. You can mix them, for example a profile on your machine and environment variables in CI.

  1. Environment variables: APPSHIP_ASC_KEY_ID, APPSHIP_ASC_ISSUER_ID, APPSHIP_ASC_KEY_PATH or APPSHIP_ASC_KEY (contents, plain or base64), APPSHIP_APPLE_ID, APPSHIP_PLAY_JSON_PATH or APPSHIP_PLAY_JSON, and APPSHIP_PROFILE.
  2. release/release.yml: paths to files in the gitignored release/keys/. Key ID and Issuer ID are not secrets and can be committed.
  3. A profile: credentials.profile: my-company, pointing to ~/.appship/credentials/my-company/.
release/release.yml, without a profile
credentials:
  ios:
    key_id: ABC123DEFG
    issuer_id: 69a6de7a-0000-0000-0000-000000000000
    key_path: release/keys/AuthKey_ABC123DEFG.p8
    apple_id: you@example.com   # optional
  android:
    json_key_path: release/keys/play-service-account.json

If a key gets committed

  1. Revoke it right away. iOS: App Store Connect → Integrations → Revoke. Android: Cloud Console → the service account → Keys → Delete.
  2. Create a new key and update your profile or CI secrets.
  3. Run git rm --cached <file>. The key stays in git history, which is why revoking it is the step that matters.
